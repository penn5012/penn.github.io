# 第 1 月：LLM API 与 TypeScript AI 应用入门

## 本月定位

本月是从“前端/移动端开发工程师”转向“AI 应用开发工程师”的起点。重点不是学习模型训练、复杂数学或算法题，而是复用已有的 TypeScript、界面开发、状态管理和 API 对接能力，建立一套正确的 LLM 应用开发心智模型，并做出第一个可演示、可测试的 AI 聊天应用。

整个月只维护一个连续演进的项目 **AI Chat Lab**：从一次普通模型调用开始，逐步加入流式响应、多轮对话、停止生成、重新生成、Markdown 渲染、历史记录、错误恢复、成本显示和基础测试。每天都在昨天的版本上增量开发，不做互不相关的小 Demo。

> 学习原则：TypeScript 为主，Python 本月不作要求；官方 SDK 和 HTTP API 并行理解；模型调用只放在服务端；先跑通最小闭环，再补工程质量。

## 前置条件

- 能使用 TypeScript 编写业务代码，理解 Promise、async/await、模块化和基本类型定义。
- 熟悉一种前端或跨端框架，如 React、Vue、Flutter、React Native 或原生移动端。
- 已安装 Git、Node.js LTS、包管理器（npm、pnpm 或 yarn）和常用 IDE。
- 具备基本的 HTTP 请求、JSON、环境变量和浏览器开发者工具使用经验。
- 准备一个可用的大模型 API 账户与少量测试额度；不得把密钥提交到客户端或 Git 仓库。

若你使用 Flutter 或原生移动端，可以保留熟悉的客户端；本月服务端示例仍以 Node.js + TypeScript 为主，客户端通过统一 HTTP/SSE 接口接入。

## 月度目标

完成本月后，你应当能够：

1. 用自己的语言解释 LLM 的 Token、上下文窗口、消息角色、温度、流式输出和幻觉。
2. 使用 TypeScript 官方 SDK 或 HTTP API 完成模型调用，并安全管理 API Key。
3. 设计清晰的聊天消息数据结构和前后端接口。
4. 实现流式输出、停止生成、重新生成、多轮对话与本地历史记录。
5. 实现超时、重试、取消、限流提示和常见 API 错误的用户友好反馈。
6. 使用 Prompt 模板和结构化输出来提高结果稳定性。
7. 粗略统计 Token、延迟和单次调用成本，开始形成“效果—速度—费用”的权衡意识。
8. 交付一个有 README、测试记录、演示视频和复盘文档的可运行项目。

## 技术栈

- **语言**：TypeScript
- **运行时**：Node.js LTS
- **客户端**：沿用你最熟悉的 React/Vue/React Native/移动端技术
- **最小服务端**：Node.js + TypeScript；可选 Express 或 Fastify，仅作为密钥代理和流式转发
- **模型接入**：一个主流 LLM 的官方 SDK，同时了解标准 HTTP 请求结构
- **流式协议**：优先 SSE；了解 `fetch` 流和 `AbortController`
- **数据保存**：先用浏览器 IndexedDB/localStorage 或移动端本地存储
- **测试**：Vitest 或 Jest；接口调试使用 curl/Bruno/Postman 任一种
- **版本管理**：Git；`.env` + `.gitignore` 管理本地配置

## 最终项目：AI Chat Lab

一个面向 Web 或移动端的 LLM 聊天应用，至少包含：

- 新建、切换、重命名和删除本地会话。
- 服务端代理模型 API，客户端代码中不存在模型密钥。
- 用户消息与模型回复的流式渲染。
- 停止生成、重新生成、复制回答和清空会话。
- 多轮对话与基础上下文裁剪。
- Markdown、代码块及基本防注入渲染。
- 空状态、加载状态、错误状态和重试入口。
- 显示本次响应耗时、粗略 Token/成本信息。
- 至少一套可切换的 System Prompt 场景。
- README、配置示例、测试清单、演示截图或 3～5 分钟录屏。

## 验收标准

- [ ] 从全新环境按 README 可在 15 分钟内运行项目。
- [ ] API Key 只存在服务端环境变量，Git 历史和客户端包中均无密钥。
- [ ] 首个流式内容在正常网络下能持续显示，界面不会等到完整回答后才刷新。
- [ ] 点击“停止生成”后，网络请求和 UI 状态都能正确终止。
- [ ] 支持至少 10 轮对话；超出设定上下文预算时有明确的裁剪策略。
- [ ] 重新生成不会破坏原有消息顺序，也不会产生重复请求。
- [ ] 至少覆盖 6 类异常：空输入、超时、断网、鉴权失败、限流、服务端错误。
- [ ] Markdown 与代码块可读，模型输出不会直接以不受控 HTML 执行。
- [ ] 至少有 5 个自动化测试和 15 条人工验收用例。
- [ ] 完成一次 20 题提示词对比测试，并保留结果与结论。
- [ ] README 中说明架构、运行方法、关键取舍、已知限制和下月改进方向。

**动手任务**：

3. 在 `docs/llm-basics.md` 画出“客户端 → 自有服务端 → 模型 API → 流式返回”的调用链。

**当日产出/验收**：形成一张调用链图和一份参数观察表；能解释为何同一问题可能得到不同答案。

**建议时间**：1.5 小时。

## 第 3 天：完成第一次服务端模型调用

**动手任务**：

**当日产出/验收**：命令行可收到模型回复；服务端日志不打印完整密钥；请求失败时不是无信息的 500 错误。

**建议时间**：2 小时。

## 第 8 天：理解流式响应与 SSE

**学习目标**：理解为什么 AI 聊天常采用流式输出，以及数据如何穿过各层。

**核心知识**：普通 HTTP 响应、SSE、WebSocket 的适用场景；Chunk、事件、连接结束、代理缓冲；首 Token 延迟与总耗时。

**动手任务**：

1. 阅读模型 SDK 的流式示例和所用框架的流响应文档。
2. 用一个本地定时字符串流模拟服务端逐段返回。
3. 使用 curl 观察原始流数据。
4. 记录 SSE 与 WebSocket 的选择理由。

**当日产出/验收**：`docs/streaming.md` 能说明本项目选 SSE/fetch 流的原因；本地模拟流能逐段到达而非一次返回。

**建议时间**：1.5 小时。

## 第 9 天：服务端转发模型流

**学习目标**：把模型输出以流方式从服务端安全转发给客户端。

**核心知识**：SDK 异步迭代器、响应头、背压的直觉理解、连接关闭、服务端异常边界；不要把供应商事件对象直接暴露给客户端。

**动手任务**：

1. 新建 `/api/chat/stream`。
2. 将模型流统一映射为 `start/delta/done/error` 事件。
3. 生成请求 ID，并在每个事件中保持可追踪性。
4. 在客户端以日志形式打印事件序列。

**当日产出/验收**：能看到 `start → 多个 delta → done`；中途异常会发送统一 `error` 或安全关闭连接。

**建议时间**：2 小时。

## 第 10 天：客户端逐字渲染

**学习目标**：流式更新助手消息且不产生重复或错序内容。

**核心知识**：增量文本拼接、不可变状态、批量渲染、自动滚动条件、流结束后的状态收口。

**动手任务**：

1. 消费 `/api/chat/stream`，将 `delta` 追加到同一助手消息。
2. 正确处理 UTF-8 片段和不完整事件。
3. 用户手动上滚时暂停强制滚到底部。
4. 收到 `done` 后标记消息完成。

**当日产出/验收**：长回答持续显示、无重复字符、无闪烁；滚动和输入框在生成期间仍可使用。

**建议时间**：2 小时。

## 第 11 天：实现停止生成

**学习目标**：让用户能够真正取消请求，而不只是停止界面更新。

**核心知识**：`AbortController`、取消信号传播、客户端断连、服务端清理、已生成部分内容的保留策略。

**动手任务**：

1. 生成期间将发送按钮切换为停止按钮。
2. 点击后取消客户端请求，并让服务端感知连接结束。
3. 将消息标记为 `cancelled`，保留已生成内容。
4. 防止取消后到达的迟发事件污染下一次请求。

**当日产出/验收**：连续测试 10 次取消均无悬挂加载；取消后可以立即开始下一次提问。

**建议时间**：2 小时。

## 第 12 天：超时、重试与错误体验

**学习目标**：针对真实网络和 API 故障设计可恢复路径。

**核心知识**：鉴权失败、限流、超时、断网、5xx；可重试与不可重试错误；指数退避只理解和使用库，不学习算法推导；避免流式请求自动重复导致重复计费。

**动手任务**：

1. 建立统一前后端错误码映射。
2. 设置连接超时和总请求超时。
3. 只对安全且尚未收到内容的请求提供自动重试；其他情况让用户手动重试。
4. 用 Mock 人为制造 401、429、500、断流和超时。

**当日产出/验收**：每类异常都有用户可理解提示和下一步操作；日志含请求 ID，不包含完整 Prompt 和密钥。

**建议时间**：2 小时。

## 第 15 天：实现真正的多轮对话

**学习目标**：让模型理解前文，同时知道客户端显示历史与模型上下文不是一回事。

**核心知识**：消息历史、上下文消息数组、System Prompt 位置、对话连续性、历史显示层与请求上下文层分离。

**当日产出/验收**：构造超长会话不会触发上下文超限；README 解释当前裁剪规则和缺点。

## 第 18 天：学习结构化输出

**学习目标**：让 LLM 返回可供界面稳定消费的数据，而不只是一段自然语言。

**核心知识**：JSON Schema、结构化输出、运行时校验、解析失败、Schema 演进；何时用结构化输出，何时用普通文本。

**动手任务**：
