# 第 6 月：用 TypeScript 自建企业知识库 RAG V1

> 适用背景：已有前端或移动端开发经验，已完成 Node.js AI 后端、Function Calling，并在第 5 月使用 Dify 跑通过知识库问答链路。
> 本月主线：TypeScript + Fastify + PostgreSQL + pgvector。
> 学习节奏：每天 1.5～2.5 小时；第 7、14、21、28 天用于周末整合；第 29～30 天完成交付验收。
> 核心原则：不刷算法题，不学习向量数学推导，不训练模型；围绕一个可运行项目学习数据处理、检索、权限和工程化。

## 1. 本月定位

第 5 月通过 Dify，你已经从用户视角理解了“上传文档—切分—索引—检索—回答”的完整链路。本月不再依赖平台替你隐藏实现，而是用 TypeScript 把关键环节逐个写出来，理解每一个工程决策会怎样影响回答质量、数据安全和后续维护。

你的前端/移动端经验在这一阶段很有价值：可以把异步上传、索引进度、引用定位、错误恢复和权限提示做成清晰的产品体验。本月需要补齐的是服务端文件处理、关系数据与向量数据建模、检索 API、增量更新和租户边界。

本月目标不是造一个通用向量数据库，也不是研究 Embedding 的数学原理，而是能够根据业务文档特征选择切分方式，安全地写入和检索向量，把证据、引用和权限贯穿到最终用户界面。

## 2. 前置条件

- 能使用 TypeScript 编写业务代码，理解 `Promise`、`async/await`、类型接口和模块拆分。
- 已有可运行的 Fastify 或 NestJS 后端；本计划以 Fastify 示例组织，使用 NestJS 时保持相同模块边界即可。
- 已掌握 REST API、环境变量、基础身份认证、PostgreSQL 和 Docker Compose。
- 已完成一个带会话记录的 Web 或移动端聊天客户端。
- 已用 Dify 创建过至少一个知识库，知道“文档、分段、检索、引用”在产品中的表现。
- 准备一个支持 Embedding 和文本生成的模型服务 API Key；Key 只允许存在于服务端。
- 本机安装 Node.js LTS、pnpm/npm、Git 和 Docker Desktop。
- 不要求掌握 Python；遇到极少数 TypeScript 难以解析的文档格式时，先记录为后续扩展，不为此切换主线。

## 3. 本月学习目标

完成本月后，你应该能够：

1. 把 Dify 中的知识库概念映射为可维护的服务端模块和数据库模型。
2. 实现 PDF、Markdown、TXT 等多文档上传、校验、解析、清洗和索引状态管理。
3. 根据文档结构设计可解释的 Chunk 策略，并保留页码、标题路径、字符位置等定位元数据。
4. 封装 Embedding Provider，支持批量调用、超时、重试、限流和模型维度校验。
5. 使用 PostgreSQL + pgvector 保存向量，以参数化 SQL 完成 Top-K 相似度检索。
6. 同时应用知识库、租户、可见范围、文件类型等元数据过滤条件。
7. 构建“查询改写暂不启用、先检索、后生成”的基础 RAG 链路，并要求模型只能依据证据回答。
8. 返回机器可验证的引用，让前端能够跳转到原文页码或文本片段。
9. 实现文档增量更新、重复上传检测、重新索引和删除。
10. 建立基础单元测试、集成测试、安全检查、结构化日志和运行文档。

## 4. 固定技术栈

| 层次 | 本月选择 | 用途 |
|---|---|---|
| 语言/运行时 | TypeScript + Node.js LTS | 复用已有前端语言经验 |
| Web 框架 | Fastify | 上传、检索、问答和文档管理 API |
| 请求校验 | TypeBox 或 Zod，沿用现有项目选择 | 校验参数、元数据和模型结构化输出 |
| 关系数据 | PostgreSQL | 知识库、文档、版本、分段和权限元数据 |
| 向量扩展 | pgvector | Embedding 存储与向量相似度检索 |
| 数据访问 | Prisma + 参数化原生 SQL | 普通 CRUD 使用 Prisma，向量操作使用受控 SQL |
| 文件上传 | `@fastify/multipart` | 限制文件类型、大小和数量 |
| 文档解析 | 成熟的 TypeScript PDF/DOCX 解析库 + 原生文本读取 | 提取正文和页码；先支持 PDF、Markdown、TXT，DOCX 为加分项 |
| 模型接入 | 模型厂商官方 Node.js SDK | Embedding 与答案生成 |
| 测试 | Vitest + Fastify `inject` | Chunk、权限、API 和 RAG 集成测试 |
| 本地部署 | Docker Compose | API、PostgreSQL/pgvector 一键启动 |

> 选择约束：Embedding 模型、向量维度和数据库字段必须一致，并通过环境变量和启动校验固定下来。更换 Embedding 模型视为一次数据迁移，需要重新建立索引，不能直接混用旧向量。

## 5. 最终项目

### 项目名称

**Enterprise Knowledge Base V1：多文档、可引用、带权限的 TypeScript RAG 系统**

### 用户场景

一个团队需要上传产品说明书、FAQ、操作手册和内部规范。成员在 Web 或移动端提问时，系统只检索其有权限访问的知识库，返回基于原文的答案和可点击引用；管理员更新或删除文档后，检索结果能同步变化。

### 最终业务链路

```text
管理员上传文档
  → 校验类型、大小、知识库归属和操作者权限
  → 保存原文件与文档记录
  → 解析和清洗正文
  → 按标题/段落切分并保留定位元数据
  → 批量生成 Embedding
  → 文档元数据、Chunk 和向量写入 PostgreSQL
  → 文档状态变为 ready

成员提问
  → 身份与租户校验
  → 生成查询向量
  → 权限条件 + 元数据条件 + Top-K 向量检索
  → 组装带编号的证据上下文
  → 模型基于证据生成答案或明确表示证据不足
  → 服务端验证引用编号
  → 前端展示答案、来源、页码和原文片段
```

### 建议核心数据模型

| 实体 | 关键字段 | 作用 |
|---|---|---|
| `KnowledgeBase` | `id`、`tenantId`、`name`、`visibility` | 知识库与租户边界 |
| `Document` | `id`、`knowledgeBaseId`、`name`、`mimeType`、`status`、`currentVersionId` | 逻辑文档和索引状态 |
| `DocumentVersion` | `id`、`documentId`、`checksum`、`parserVersion`、`createdBy` | 增量更新和重复检测 |
| `DocumentChunk` | `id`、`versionId`、`content`、`chunkIndex`、`sectionPath`、`pageNumber`、`startOffset`、`endOffset`、`metadata`、`embedding` | 检索内容、向量和原文定位 |
| `KnowledgeBaseMember` | `knowledgeBaseId`、`userId`、`role` | 管理员、编辑者、读取者权限 |

### 建议 API

```text
POST   /api/knowledge-bases/:kbId/documents
GET    /api/knowledge-bases/:kbId/documents
GET    /api/documents/:documentId
POST   /api/documents/:documentId/reindex
DELETE /api/documents/:documentId
POST   /api/knowledge-bases/:kbId/retrieve
POST   /api/knowledge-bases/:kbId/chat
GET    /api/documents/:documentId/chunks/:chunkId/context
```

## 6. 范围边界

本月刻意不做以下内容：

- 不推导余弦相似度、向量空间或 Transformer 数学公式。
- 不训练或微调 Embedding/生成模型。
- 不刷算法题，不手写 ANN 索引。
- 不引入 Agent、自主规划或多 Agent；RAG 链路保持确定、可调试。
- 不追求一次支持所有办公文件；先把 PDF、Markdown、TXT 做稳定。
- 不在本月深做混合检索、Query Rewrite、Rerank 和完整评测平台；这些是第 7 月主线。

## 7. 30 天逐日计划

### 第 1 天：从 Dify 反推自建 RAG 链路

- **学习目标**：把第 5 月看到的平台能力拆成可以自己实现的服务模块。
- **核心知识**：摄取链路与查询链路的区别；原文件、结构化正文、Chunk、Embedding、检索结果、答案和引用之间的关系。
- **动手任务**：在 Dify 中上传一份熟悉的文档，记录它能配置的切分、检索和引用选项；画出自建版本的上传链路与提问链路；列出哪些由后端完成、哪些由前端展示。
- **当日产出/验收**：提交 `docs/rag-flow.md` 或等价设计笔记，包含两张流程图、至少 5 个失败场景和本月明确不做的功能；能口头解释为什么“上传成功”不等于“可检索”。
- **建议时间**：1.5～2 小时。

### 第 2 天：建立需求、用户故事和验收样本

- **学习目标**：先用业务问题定义知识库，而不是先选向量库参数。
- **核心知识**：知识库管理员与普通成员；数据源范围；回答有证据、证据不足、无权限三种不同结果；功能验收和效果验收的区别。
- **动手任务**：选择一个具体领域，例如产品说明书、开发规范或售后手册；准备 10～20 份可合法使用的测试文档；写出管理员上传/更新/删除、成员提问/查看引用的用户故事；人工整理 10 条基础问题及期望来源。
- **当日产出/验收**：形成一页需求说明和首版 `smoke-questions` 数据；每个问题都标明目标文档或“应拒答”，不包含真实公司敏感数据。
- **建议时间**：2 小时。

### 第 3 天：初始化模块与接口契约

- **学习目标**：在已有 AI 后端中建立清晰的 RAG 边界。
- **核心知识**：Document Service、Parser、Chunker、Embedding Provider、Retriever 和 Rag Service 的单一职责；接口先于具体厂商实现。
- **动手任务**：建立 `documents`、`indexing`、`retrieval`、`rag` 模块；定义 `ParsedDocument`、`ChunkDraft`、`RetrievedChunk`、`Citation` 等 TypeScript 类型；创建空实现和最小健康检查。
- **当日产出/验收**：项目能通过 `typecheck`、`lint` 和启动检查；RAG 路由不直接导入模型厂商 SDK；各核心接口的输入输出有类型注释。
- **建议时间**：1.5～2 小时。

### 第 4 天：启动 PostgreSQL + pgvector

- **学习目标**：让项目具备同时保存关系元数据和向量的数据库环境。
- **核心知识**：PostgreSQL 扩展、迁移、连接池、向量字段维度、开发数据库和测试数据库隔离。
- **动手任务**：在 Docker Compose 中使用包含 pgvector 的 PostgreSQL 镜像；通过迁移启用 `vector` 扩展；增加 `EMBEDDING_MODEL` 和 `EMBEDDING_DIMENSIONS` 配置校验；创建单独测试数据库配置。
- **当日产出/验收**：API 和数据库可以一键启动；SQL 查询确认 `vector` 扩展已启用；配置缺失或维度非法时服务拒绝启动并给出明确错误。
- **建议时间**：2～2.5 小时。

### 第 5 天：设计知识库、文档、版本与 Chunk 表

- **学习目标**：用数据模型支持多文档、更新、删除、引用和权限。
- **核心知识**：逻辑文档与物理版本分离；Checksum 去重；索引状态；Chunk 稳定标识；JSONB 元数据；向量维度必须固定。
- **动手任务**：建立 `KnowledgeBase`、`Document`、`DocumentVersion`、`DocumentChunk`、`KnowledgeBaseMember` 模型；向量字段通过 SQL 迁移建立；为租户、知识库、版本、状态和常用过滤字段创建必要索引。
- **当日产出/验收**：迁移可在空数据库完整执行；画出 ER 图；能够说明更新文档时旧版本何时保留、何时失效，以及每个 Chunk 如何回到原文。
- **建议时间**：2～2.5 小时。

### 第 6 天：实现安全的文档上传 API

- **学习目标**：安全接收原始文档并管理上传状态。
- **核心知识**：Multipart 流式接收；MIME 与扩展名双重检查；文件大小/数量限制；随机存储名；原文件名不可直接作为磁盘路径；状态机 `uploaded → parsing → indexing → ready/failed`。
- **动手任务**：实现上传接口；限制白名单类型和单文件大小；计算 SHA-256；把本地文件系统封装成 `FileStorageProvider`，以便未来替换对象存储；写入文档和版本记录。
- **当日产出/验收**：合法 PDF/MD/TXT 能上传并返回文档 ID；超大文件、不支持类型、空文件和伪造路径名被拒绝；真实文件名仅作元数据保存；API Key 和本地绝对路径不返回客户端。
- **建议时间**：2～2.5 小时。

### 第 7 天：第一周整合——从上传到可追踪状态

- **学习目标**：形成最小但完整的文档管理骨架。
- **核心知识**：异步任务的用户体验；轮询状态；失败原因可观测但不可泄露内部堆栈；重新处理入口。
- **动手任务**：补齐文档列表、详情和状态查询 API；在前端做上传区、文件列表、状态徽标和失败提示；统一错误码；更新本地启动说明并回归前 6 天功能。
- **当日产出/验收**：管理员可上传多份文档并看到每份文件状态；刷新页面后记录仍存在；失败项能显示安全的原因和“重试”入口；完成一份第一周问题清单。
- **建议时间**：2～2.5 小时，周末整合。

### 第 8 天：实现文档解析适配层

- **学习目标**：将不同文件格式统一成带定位信息的正文结构。
- **核心知识**：Parser Registry；按 MIME 选择解析器；PDF 页码；Markdown 标题层级；纯文本编码；解析结果与原文件分离。
- **动手任务**：定义 `DocumentParser` 接口；实现 TXT/Markdown 解析器和 PDF 解析器；输出统一的 `ParsedBlock`，至少包含文本、页码或标题路径、原始顺序；为无法解析和密码保护 PDF 返回明确错误。
- **当日产出/验收**：三种格式各有一份固定测试样本；解析结果顺序正确、正文非空；PDF 至少能保留页码，Markdown 至少能保留标题路径。
- **建议时间**：2～2.5 小时。

### 第 9 天：清洗正文但保留可追溯性

- **学习目标**：去掉影响检索的噪声，同时避免把有意义的格式清洗掉。
- **核心知识**：Unicode 规范化；空白合并；重复页眉页脚；空页；断行和连字符；表格、代码块、列表不应被无差别压平。
- **动手任务**：建立可组合的 Cleaner Pipeline；实现基础空白清洗、空块移除和可配置页眉页脚去重；保存 `rawText` 摘要或原始定位，不覆盖原文件；为每项规则写前后对比用例。
- **当日产出/验收**：测试样本清洗后语义未被破坏；代码块、编号列表和产品型号仍完整；清洗规则带版本号，失败时能定位到具体规则。
- **建议时间**：2 小时。

### 第 10 天：设计面向业务的 Chunk 策略

- **学习目标**：根据说明书和规范文档的结构选择切分方法。
- **核心知识**：按标题/段落优先切分；超长块再按字符或 Token 近似长度拆分；Overlap 的作用和代价；Chunk 过大与过小的产品后果；本月不做语义切分算法研究。
- **动手任务**：实现“标题层级 → 段落 → 最大长度兜底”的 Chunker；配置目标长度、最大长度和重叠范围；给每个 Chunk 附加文档名、标题路径、页码、前后字符偏移和 `chunkIndex`。
- **当日产出/验收**：同一输入与同一配置产生稳定结果；不存在空 Chunk；任何 Chunk 都能通过元数据追溯到文档位置；在设计笔记中解释当前参数为什么适合测试文档。
- **建议时间**：2～2.5 小时。

### 第 11 天：制作 Chunk 可视化调试页与测试

- **学习目标**：利用前端优势让切分问题可见、可比较。
- **核心知识**：切分边界检查；上下文断裂；重复内容；配置预览；可视化调试比盲目改参数更可靠。
- **动手任务**：实现“仅解析并预览，不写向量”的调试 API；前端按文档顺序展示 Chunk、长度、页码、标题路径和重叠片段；为纯文本、Markdown、分页 PDF、超长段落和空白文档编写单元测试。
- **当日产出/验收**：可在界面调整两组 Chunk 参数并对比结果；至少 5 类样本测试通过；人工抽查 30 个 Chunk，没有明显标题丢失或句子大面积截断。
- **建议时间**：2～2.5 小时。

### 第 12 天：封装 Embedding Provider

- **学习目标**：用稳定接口调用 Embedding API，而不是把厂商 SDK 散落在业务代码里。
- **核心知识**：单条与批量 Embedding；模型和维度；输入长度限制；批大小；超时、有限重试、指数退避；使用量与成本日志。
- **动手任务**：定义 `EmbeddingProvider.embedTexts()`；实现一个真实 Provider 和一个固定向量 Fake Provider；分批提交 Chunk；校验返回数量和维度；对超时、429、5xx 做有限重试，其他 4xx 快速失败。
- **当日产出/验收**：输入 N 段返回 N 个固定维度向量；日志记录模型、批次数、耗时和输入数量但不记录敏感全文；Fake Provider 可供单元测试离线运行。
- **建议时间**：2～2.5 小时。

### 第 13 天：建立可恢复的索引流水线

- **学习目标**：把解析、清洗、切分、Embedding 和写库连接成可重试流程。
- **核心知识**：Pipeline 阶段；状态更新；事务边界；批量写入；幂等任务；不要长时间持有数据库事务等待外部 API。
- **动手任务**：实现 `IndexDocumentUseCase`：读取原文件、解析、清洗、切分、批量生成向量、事务性写入新版本 Chunk、切换当前版本；保存失败阶段和可读错误；为重新执行使用稳定任务键。
- **当日产出/验收**：一份多页文档最终变为 `ready` 且数据库存在对应 Chunk/向量；Embedding 中途失败时不会把半成品版本设为当前版本；重试不会重复插入同一版本 Chunk。
- **建议时间**：2.5 小时。

### 第 14 天：第二周整合——多文档摄取闭环

- **学习目标**：验证系统能连续处理多种文档，而不只适配一个示例。
- **核心知识**：批量操作的局部失败；索引进度；失败重试；数据量与时间/成本基线。
- **动手任务**：上传并索引至少 10 份 PDF/MD/TXT；前端显示解析、切分、Embedding、写入阶段和完成数量；抽查 Chunk；修复编码、空页、长段落或重复页眉问题；记录耗时和 Embedding 调用次数。
- **当日产出/验收**：至少 10 份文档中 9 份成功索引，失败文档有明确原因且不影响其他文档；每份 ready 文档都有 Chunk；形成一份摄取基线表和第二周复盘。
- **建议时间**：2～2.5 小时，周末整合。

### 第 15 天：实现 pgvector Top-K 检索

- **学习目标**：从查询文本得到最相关的若干 Chunk。
- **核心知识**：查询 Embedding；pgvector 距离操作符的结果含义；Top-K；相似度分数只用于排序和初步阈值，不等同于答案正确率；SQL 参数化。
- **动手任务**：在 Repository 中实现向量查询；输入查询向量、知识库 ID 和 K，返回 Chunk 内容、文档信息、定位元数据与分数；用白名单限制 K 的最大值；禁止字符串拼接向量和过滤条件。
- **当日产出/验收**：对 10 条基础问题能返回按分数排序的结果；结果全部来自指定知识库；非法 K 被拒绝；数据库查询日志中没有完整用户问题或文档正文。
- **建议时间**：2～2.5 小时。

### 第 16 天：把元数据和权限过滤放进检索查询

- **学习目标**：保证“相关”结果同时也是“允许访问”的结果。
- **核心知识**：检索前过滤；租户隔离；知识库成员；文档状态；文件类型、标签、日期等业务元数据；应用层过滤太晚会造成数据泄露和无效 Top-K。
- **动手任务**：为检索查询增加 `tenantId`、`userId`、`knowledgeBaseId`、`ready/currentVersion` 必选条件；实现文件类型、标签、时间范围等可选过滤；用结构化对象构建允许的条件，不接受任意 SQL 字段名。
- **当日产出/验收**：同一查询在不同租户或不同成员身份下返回不同且正确的数据；非成员得到 403 或空结果，不暴露文档是否存在；测试证明过滤发生在 Top-K 之前。
- **建议时间**：2～2.5 小时。

### 第 17 天：设计独立检索 API

- **学习目标**：在生成答案前单独观察并调试检索质量。
- **核心知识**：`retrieve` 与 `chat` 分离；请求校验；结果去重；阈值；邻近片段；调试信息和正式响应的边界。
- **动手任务**：实现 `POST /retrieve`；请求支持问题、K 和白名单过滤；响应包含 Chunk ID、摘要、分数、文档名、页码/标题路径；增加开发环境可选调试字段；相邻 Chunk 只作为展示上下文，不重复占用 Top-K 名额。
- **当日产出/验收**：前端检索调试页能输入问题、切换过滤条件并查看结果；空查询、超长查询和越权请求被拒绝；10 条冒烟问题均保存一次人工判断。
- **建议时间**：2 小时。

### 第 18 天：基于证据生成答案

- **学习目标**：把检索结果转为受约束的答案，而不是让模型自由发挥。
- **核心知识**：System Prompt 与证据边界；把文档内容视为不可信数据；证据编号；上下文预算；证据不足时拒答；模型温度与稳定性。
- **动手任务**：实现 Rag Service：检索、筛选、按预算拼接证据、调用生成模型；提示词要求只依据编号证据、无法支持时明确说明；将用户问题与证据放在不同结构区块；记录检索和生成两个阶段耗时。
- **当日产出/验收**：已知问题能依据命中文档回答；无关问题明确表示知识库证据不足；把“忽略规则”写进测试文档后，系统不会把文档指令当作系统命令执行。
- **建议时间**：2～2.5 小时。

### 第 19 天：建立可验证的引用协议

- **学习目标**：让每条引用都能被服务端验证并由客户端定位原文。
- **核心知识**：引用不是模型随意生成的文件名；证据 ID 白名单；结构化输出；Chunk 到文档版本、页码、标题路径和字符偏移的映射；过期版本处理。
- **动手任务**：定义答案响应 `{ answer, citations[] }`；每个证据分配短编号；模型只返回用到的编号；服务端丢弃不在检索集合中的编号并把编号展开为可信元数据；实现原文上下文 API。
- **当日产出/验收**：引用中的文档 ID、Chunk ID、版本和定位全部来自数据库，不采信模型自报字段；点击引用 API 能取得原文前后文；伪造引用编号不会被返回给客户端。

### 第 20 天：完成文档管理前端

- **学习目标**：把摄取链路做成可操作、可恢复的产品功能。

### 第 21 天：第三周整合——问答、引用与原文定位

- **学习目标**：完成从提问到证据回看的用户闭环。
- **核心知识**：流式答案与最终引用的事件设计；引用卡片；PDF 页码、Markdown 标题和文本片段的不同定位方式；加载、空结果和部分失败状态。

### 第 22 天：实现重复检测与增量更新

- **学习目标**：更新一份文档时只产生必要的新版本，并且不中断旧版本查询。
- **核心知识**：内容 Checksum；文件名不能作为唯一判断；写新版本、验证完成、原子切换当前版本；旧版本保留策略；Chunk ID 稳定性和缓存失效。

### 第 23 天：实现删除、重新索引与一致性检查

- **当日产出/验收**：删除文档后任何用户都无法再检索到它；数据库无孤儿 Chunk；重新索引不会生成重复当前版本；删除或重建失败可追踪且可再次执行。

### 第 25 天：处理并发、幂等、重试和任务恢复

## 8. 月末验收清单

### 功能验收

- [ ] 支持一个知识库上传至少 10 份 PDF、Markdown、TXT 文档，并能逐份查看索引状态。
- [ ] 文档经过解析、清洗、结构化 Chunk、Embedding 后写入 PostgreSQL + pgvector。
- [ ] 检索 API 支持 Top-K、知识库范围和至少两类元数据过滤。
- [ ] 问答 API 只依据检索证据回答，证据不足时明确拒答。
- [ ] 引用由服务端验证，能够定位文档、版本、页码/标题路径和原文片段。
- [ ] 更新期间旧版本持续可用；新版本完成后原子切换；相同内容不会重复索引。
- [ ] 删除后文档、Chunk 和向量不再参与检索，且没有孤儿数据。
- [ ] 前端具备上传、状态、失败重试、文档列表、聊天、引用查看和原文定位体验。

### 工程验收

- [ ] Embedding、文件存储、Parser、Chunker、Retriever 和 LLM 均通过接口隔离。
- [ ] 普通关系数据由 Prisma 管理，向量 SQL 使用参数化查询，不拼接用户输入。
- [ ] 索引任务具备状态、幂等、有限重试、失败原因和恢复策略。
- [ ] `typecheck`、基础单测和集成测试可一条命令运行。
- [ ] Docker Compose 可启动 API 与 pgvector 数据库，README 能让他人复现。
- [ ] 日志可区分上传、解析、Embedding、写库、检索和生成耗时，且不泄露正文、Key 或内部路径。

### 权限与安全验收

- [ ] 每次文档和检索操作都校验租户、成员身份和角色。
- [ ] 权限过滤在 Top-K 查询内完成，不依靠返回后过滤。
- [ ] 跨租户用户无法通过猜测 ID 查看文档、Chunk、引用或检索结果。
- [ ] 上传接口限制文件类型、大小、数量和解析时间，文件名不能影响存储路径。
- [ ] 文档中的 Prompt Injection 文本不能改变系统规则或触发外部工具。

### 基础质量基线

- [ ] 至少建立 20 条带期望来源的冒烟问题，包括可回答、不可回答、过滤和越权四类。
- [ ] 每条问题记录 Top-K 是否出现目标片段、答案是否受证据支持、引用是否正确。
- [ ] 记录索引耗时、查询检索耗时、生成耗时和模型调用成本。
- [ ] 不为追求好看的数字删除失败样本；所有问题进入第 7 月实验集。

## 9. 本月复盘模板

月末用下面的问题写一篇项目复盘：

1. Dify 中最容易使用、但自建后最复杂的环节是什么？复杂性来自数据、权限还是工程状态？
2. 当前文档类型和业务问题为什么适合这套 Chunk 策略？有哪些问题明显检索不到？
3. 如何证明引用是真实检索证据，而不是模型编造的文件名？
4. 文档更新失败时，为什么用户仍能查询旧版本？数据库中如何实现？
5. 权限条件放在检索后过滤会有什么风险？本项目如何避免？
6. 哪一步最耗时、哪一步成本最高？数据依据是什么？
7. 当前 20 条问题中，失败主要来自解析、切分、召回还是生成？
8. 如果文档从 10 份增长到 1 万份，最先需要改造的三处是什么？

## 10. 与第 7 月高级 RAG 的衔接

本月交付的是可运行、可追溯、有权限边界的基础 RAG，而不是检索效果终点。第 7 月直接复用本月的数据库、引用协议、20 条问题和日志基线，重点做：

1. 把 20 条冒烟问题扩充为不少于 100 条、按场景分层的评测集。
2. 建立 Recall@K、MRR/命中排名、答案正确率、引用正确率、无依据回答率、延迟和成本指标。
3. 在同一评测集上比较不同 Chunk 大小、Overlap、Top-K 和相似度阈值，避免凭感觉调参。
4. 引入关键词 + 向量的混合检索，改善产品型号、错误码、缩写和精确术语的查找。
5. 尝试 Query Rewrite、Rerank、邻近 Chunk 扩展和更细的元数据过滤，并保留可回滚的实验记录。
6. 增加文档版本、增量同步、多租户权限和评测回归的自动化，逐步走向企业知识库 V2。

进入第 7 月前，务必保留本月的原始失败案例和基线结果。高级 RAG 的价值不在于堆叠更多组件，而在于能用评测数据说明：哪个改动解决了哪类问题、带来多少收益，又增加了多少延迟与成本。
