# 第 5 月学习计划：用 Dify 跑通知识库与 RAG 全链路

> 适用背景：已有前端或移动端开发经验，以 TypeScript 为主、Python 为辅，不走算法训练路线。
> 本月投入：每天 1.5～2.5 小时，30 天约 55～65 小时。
> 本月关键词：需求分析、数据治理、分段、索引、召回、元数据、引用、Chatflow、Workflow、API 集成、反馈、评测。

## 一、本月定位

前 4 个月已经完成 LLM 应用、AI 交互、服务端接入和工具调用基础。本月不急着自建向量检索代码，而是使用 Dify 把 RAG（检索增强生成）的完整业务链路跑通，建立“一个知识库为什么有效或无效”的工程直觉。

本月重点不是学复杂数学，也不是研究 Embedding 模型训练，而是掌握以下决策能力：

- 什么需求适合知识库，什么需求应该实时调用数据库或业务 API。
- 如何盘点、清洗、切分和管理企业文档。
- 如何通过分段、元数据、召回参数和提示词改善回答。
- 如何要求回答引用证据，并在证据不足时拒绝猜测。
- 如何把 Dify 知识库接入 Chatflow、Workflow 以及已有 Web/移动端产品。
- 如何通过问题集、用户反馈和日志判断知识库是否真正可用。

## 二、前置要求

- 能使用 Git，能读写基础 TypeScript。
- 理解 HTTP、JSON、REST API 和环境变量。
- 已接触大模型 API、Prompt、多轮对话和流式响应。
- 本机可运行 Docker；优先使用 Dify 云端快速开始，也可使用本地部署环境。
- 准备一套可公开或可安全使用的产品文档，例如产品说明书、FAQ、技术手册、故障处理指南。

## 三、本月学习目标

完成本月后，应能独立做到：

1. 将模糊的“做一个企业知识助手”需求拆成用户、问题、数据源、权限、更新频率和验收指标。
2. 解释 RAG 的业务链路：文档采集 → 清洗 → 分段 → 向量化/索引 → 召回 → 生成 → 引用 → 反馈。
3. 在 Dify 中创建、配置、调试和更新知识库。
4. 根据文档结构设计分段策略与元数据，而不是只接受默认配置。
5. 在 Chatflow/Workflow 中组合问题澄清、知识检索、回答生成、证据不足分支和反馈记录。
6. 通过 API 将知识助手接入现有 Web 或移动端，并安全处理密钥。
7. 建立至少 50 条基础评测问题，并用结果驱动一次有记录的优化。

## 四、建议技术栈

- 知识库与工作流：Dify
- 客户端：已有 React、Vue、Flutter、React Native 或原生项目，任选其一
- API 代理：Node.js + TypeScript，可使用现有 Fastify/NestJS 项目
- 数据整理：Markdown、CSV；必要时使用少量 Python/Node.js 脚本
- 调试：浏览器开发者工具、curl/Postman/Apifox
- 版本管理：Git
- 项目记录：Markdown + 表格

## 五、本月主项目

### 产品说明书 / 技术文档知识助手

面向产品用户或内部支持人员，提供基于文档证据的问答服务。

核心能力：

- 导入产品说明书、FAQ、故障排查手册和版本说明。
- 支持产品型号、文档类型、版本、语言等元数据过滤。
- 回答中显示文档名称、章节或分段来源。
- 对问题缺少产品型号、版本等关键信息时先追问。
- 检索不到可靠证据时明确说明“不确定”，不编造答案。
- 支持 Web 或移动端流式对话、引用展开、点赞/点踩和问题反馈。
- 维护一套可重复执行的基础评测集。

建议目录：

```text
product-knowledge-assistant/
├── docs/raw/                  # 原始文档
├── docs/cleaned/              # 清洗后的 Markdown/文本
├── dataset/document-inventory.csv
├── eval/rag-eval.csv          # 评测问题与预期证据
├── notes/decision-log.md      # 分段、元数据、参数决策
├── screenshots/               # Dify 配置与测试截图
└── README.md
```

## 六、30 天逐日计划

### 第 1 天：明确场景与用户边界

- **学习目标**：把“做知识库”转化为可验证的产品问题。
- **核心知识**：知识问答适合回答相对稳定且有文档依据的问题；订单状态、库存、余额等实时数据应通过业务 API 获取。
- **动手任务**：选择一个熟悉的产品，写出目标用户、Top 10 高频问题、使用入口、不能回答的范围和可能造成的业务风险。
- **当日产出/验收**：完成 `需求说明 v0.1`，至少包含 2 类用户、10 个问题、5 个明确的能力边界；能够说明为什么此场景需要 RAG。
- **建议时间**：1.5 小时。

### 第 2 天：把需求转成成功指标

- **学习目标**：建立“不是能回答就算完成”的验收意识。
- **核心知识**：业务指标与技术指标的区别；正确率、引用正确率、无依据回答率、响应时间、问题解决率、用户反馈率。
- **动手任务**：为助手定义上线前门槛，区分关键问题、普通问题和超范围问题；设计人工兜底规则。
- **当日产出/验收**：完成指标表，至少定义 6 个指标、计算方法、目标值和数据来源；明确 3 类失败样例。
- **建议时间**：1.5～2 小时。

### 第 3 天：盘点数据源

- **学习目标**：知道知识质量首先取决于数据质量。
- **核心知识**：权威来源、文档所有者、格式、时效性、重复、冲突、敏感性、更新周期。
- **动手任务**：收集 15～30 份说明书、FAQ、版本说明或技术文章；为每份文档登记来源、负责人、版本和更新时间。
- **当日产出/验收**：完成 `document-inventory.csv`；每条记录至少包含文件名、类型、产品、版本、语言、更新时间、权威级别和是否可公开。
- **建议时间**：2 小时。

### 第 4 天：识别脏数据与权限风险

- **学习目标**：避免把冲突、过期或敏感内容直接放入知识库。
- **核心知识**：重复文档、过期版本、扫描件、页眉页脚、目录噪声、个人信息、密钥、内部权限信息。
- **动手任务**：抽查全部数据源，对重复、冲突、敏感和解析困难的文档做标记；定义“可导入、需处理、禁止导入”三级状态。
- **当日产出/验收**：形成数据风险清单；至少识别 5 种风险，并为每种风险写出处理方式和负责人。
- **建议时间**：1.5～2 小时。

### 第 5 天：完成第一批文档清洗

- **学习目标**：将原始资料变成结构清晰、可检索的文本。
- **核心知识**：标题层级、段落边界、列表、表格转写、图片说明、代码块、页眉页脚去除。
- **动手任务**：清洗 3～5 份代表性文档，优先转为 Markdown；保留章节标题、产品型号和版本信息。
- **当日产出/验收**：得到第一批 `docs/cleaned/` 文件；随机检查 10 个段落，内容完整、无明显页眉页脚噪声、标题层级正确。
- **建议时间**：2～2.5 小时。

### 第 6 天：理解 RAG 全链路

- **学习目标**：能用业务语言解释一次知识问答发生了什么。
- **核心知识**：文档分段、Embedding、索引、Query、召回、上下文拼接、生成、引用；Embedding 只需理解为语义表示，无需推导数学公式。
- **动手任务**：画出从“上传文档”到“用户看到答案”的流程，并标注每一步可能失败的原因。
- **当日产出/验收**：完成一张 RAG 流程图和故障点清单；能口头解释 3 分钟，不使用模型训练术语堆砌。
- **建议时间**：1.5 小时。

### 第 7 天：周末整合——建立 Dify 首个知识库

- **学习目标**：让第一条基于文档证据的回答跑通。
- **核心知识**：Dify 数据集/知识库、文档导入、索引模式、分段预览、召回测试。
- **动手任务**：创建知识库，导入第一批清洗文档；检查分段预览，使用第 1 天的问题进行检索测试。
- **当日产出/验收**：知识库可用；保存配置与 5 个检索测试截图，至少 3 个问题能召回正确文档片段；写出第一次失败观察。
- **建议时间**：2.5 小时。

### 第 8 天：理解分段为什么影响检索

- **学习目标**：理解分段不是越小或越大越好。
- **核心知识**：Chunk 粒度、重叠、上下文完整性、标题丢失、一个分段只表达一个主题、父子段思想。
- **动手任务**：选择同一份文档，设计“小段、中段、按章节”三种策略，并预测它们对 10 个问题的影响。
- **当日产出/验收**：完成分段实验设计表，包含策略、适用文档、优点、风险和预期结果。
- **建议时间**：1.5～2 小时。

### 第 9 天：执行分段对照实验

- **学习目标**：用实际召回结果选择策略，而不是凭感觉调参。
- **核心知识**：检索结果的相关性、完整性、冗余度；Top-K 结果观察。
- **动手任务**：将同一文档按三种策略导入测试知识库，对同一组 10 个问题执行召回测试并记录首条命中情况。
- **当日产出/验收**：完成分段对照表；为主文档选出默认策略，并写明至少 3 条证据。
- **建议时间**：2～2.5 小时。

### 第 10 天：理解索引与 Embedding 的工程意义

- **学习目标**：会做模型与索引选型，但不进入训练和数学细节。
- **核心知识**：语义相似、语言覆盖、文本长度、成本、延迟；高质量索引与经济索引的取舍。
- **动手任务**：记录当前 Dify 可选配置，围绕中文支持、成本、延迟和隐私做一页选型说明；用同义问法测试语义召回。
- **当日产出/验收**：完成 `索引与 Embedding 选型记录`；至少用 5 组不同措辞验证语义检索，并记录成功/失败。
- **建议时间**：1.5～2 小时。

### 第 11 天：设计元数据体系

- **学习目标**：让检索可以按业务属性缩小范围。
- **核心知识**：元数据字段、可枚举值、文档级与分段级属性、过滤条件、字段一致性。
- **动手任务**：为产品文档设计产品线、型号、版本、语言、文档类型、发布日期、权限等级等字段与命名规则。
- **当日产出/验收**：完成元数据字典，至少 6 个字段；每个字段包含类型、示例、是否必填、值域和维护规则。
- **建议时间**：1.5 小时。

### 第 12 天：补齐元数据并验证过滤

- **学习目标**：验证元数据能解决版本混淆和产品串答。
- **核心知识**：过滤优先于全库检索的场景；错误元数据会直接造成漏召回。
- **动手任务**：给已导入文档补充元数据；设计跨型号、跨版本的易混淆问题，对比过滤前后的结果。
- **当日产出/验收**：至少 10 份文档完成元数据；完成 6 组对照测试，能展示过滤减少错误召回的案例。
- **建议时间**：2 小时。

### 第 13 天：理解召回参数与结果阅读

- **学习目标**：学会看检索结果，而不只看最终回答。
- **核心知识**：Top-K、相似度阈值、召回不足、噪声召回、结果去重；参数之间的基本权衡。
- **动手任务**：使用明确问题、模糊问题、口语问题、错误型号问题分别测试不同 Top-K/阈值设置。
- **当日产出/验收**：形成参数实验记录，至少 12 次测试；选出一组当前基线配置并说明原因。
- **建议时间**：2 小时。

### 第 14 天：周末整合——知识库基线版本

- **学习目标**：把清洗、分段、元数据和召回配置合成可复现版本。
- **核心知识**：基线、配置版本、变更记录、可复现实验。
- **动手任务**：整理全部文档；统一字段和分段规则；导入 10～20 份正式文档；执行 20 个检索问题并记录。
- **当日产出/验收**：发布“知识库基线 v1”；20 个问题中大多数能在 Top-K 中找到预期片段；配置、数据版本和已知问题全部写入决策日志。
- **建议时间**：2.5 小时。

### 第 15 天：在 Chatflow 中接入知识检索

- **学习目标**：从单独测试知识库进入可对话应用。
- **核心知识**：开始节点、用户输入、知识检索节点、LLM 节点、回答节点、变量映射。
- **动手任务**：创建 Chatflow，把用户问题传入知识检索节点，再将检索结果作为上下文交给模型生成回答。
- **当日产出/验收**：可完成一轮带知识上下文的问答；保存流程截图，测试 10 个问题且流程无变量错误。
- **建议时间**：2 小时。

### 第 16 天：编写受证据约束的回答提示词

- **学习目标**：减少模型脱离文档自由发挥。
- **核心知识**：角色、任务、证据范围、输出格式、拒答条件、冲突信息处理、避免暴露内部提示词。
- **动手任务**：写一版回答 Prompt，要求仅依据检索内容回答、区分事实与建议、证据不足时说明缺失信息。
- **当日产出/验收**：完成 Prompt v1；用 5 个有答案问题和 5 个无答案问题测试，无答案问题不会强行编造具体结论。
- **建议时间**：1.5～2 小时。

### 第 17 天：实现引用与来源展示

- **学习目标**：让用户能验证回答依据。
- **核心知识**：引用的文档名、章节、片段、链接；引用完整性和引用相关性。
- **动手任务**：配置回答中的来源/引用；设计客户端引用卡片字段，包括文档名、章节、摘要和展开入口。
- **当日产出/验收**：至少 10 个回答显示可识别来源；抽查每条引用确实支持对应结论，不只是在同一文档中出现。
- **建议时间**：2 小时。

### 第 18 天：实现问题澄清分支

- **学习目标**：信息不足时先提问，而不是检索错误范围。
- **核心知识**：必填业务实体、意图识别、结构化提取、条件分支、会话变量。
- **动手任务**：在 Chatflow 中识别产品型号和版本；缺少关键信息时追问，信息完整时按元数据进入检索。
- **当日产出/验收**：覆盖“信息完整、缺型号、缺版本、超范围”四条路径；每条路径至少通过 2 个测试问题。
- **建议时间**：2～2.5 小时。

### 第 19 天：处理证据不足与冲突

- **学习目标**：建立安全、可信的失败体验。
- **核心知识**：低相关度、空召回、文档冲突、过期内容、转人工与反馈入口。
- **动手任务**：增加空召回和低可信度分支；当来源冲突时展示版本和日期，不替用户武断选择；提供提交反馈入口。
- **当日产出/验收**：至少设计并通过 6 个负向测试；输出包括缺失信息说明、建议下一步和人工入口。
- **建议时间**：2 小时。

### 第 20 天：从 Chatflow 扩展到 Workflow

- **学习目标**：理解对话流程与可复用业务流程的差别。
- **核心知识**：Chatflow 面向多轮会话；Workflow 适合可组合的批处理或业务步骤；输入输出契约和节点职责。
- **动手任务**：创建一个“提交问题 → 提取产品信息 → 检索 → 生成结构化答复”的 Workflow；输出 answer、citations、confidence、need_human。
- **当日产出/验收**：Workflow 可通过手动运行；输出字段结构稳定，至少 10 个测试不因缺字段失败。
- **建议时间**：2 小时。

### 第 21 天：周末整合——完成知识助手 v1

- **学习目标**：形成一条端到端且可演示的业务链路。
- **核心知识**：流程联调、测试矩阵、异常路径、发布版本。
- **动手任务**：整合追问、元数据检索、证据回答、引用、拒答和反馈；使用正常、模糊、错误、超范围问题做回归。
- **当日产出/验收**：发布知识助手 v1；完成至少 25 个用例的测试记录，主流程和 4 类异常流程均可演示。
- **建议时间**：2.5 小时。

### 第 22 天：理解 Dify API 与安全边界

- **学习目标**：准备把工作流接入已有产品，而不是停留在 Dify 页面。
- **核心知识**：应用 API、鉴权、会话 ID、流式/阻塞响应、用户标识、服务端代理、密钥不能放客户端。
- **动手任务**：阅读当前应用 API 说明，使用 curl/Postman/Apifox 从服务端环境变量调用一次对话或 Workflow。
- **当日产出/验收**：保存脱敏的请求/响应示例；能解释每个关键字段；仓库和客户端构建产物中均无 Dify 密钥。
- **建议时间**：1.5～2 小时。

### 第 23 天：编写 TypeScript 服务端代理

- **学习目标**：用熟悉的技术栈建立安全、可维护的接入层。
- **核心知识**：API 代理、输入校验、超时、错误映射、请求 ID、日志脱敏。
- **动手任务**：在 Node.js 服务中增加知识助手接口；校验 question、conversationId、product/版本字段并转发 Dify 请求。
- **当日产出/验收**：接口可运行；覆盖成功、参数错误、上游超时和上游异常四种情况；日志不记录密钥和完整敏感内容。
- **建议时间**：2～2.5 小时。

### 第 24 天：接入 Web 或移动端流式对话

- **学习目标**：把知识助手接入真实交互界面。
- **核心知识**：流式事件解析、消息状态、取消请求、重连/失败提示、会话关联。
- **动手任务**：任选现有 Web/移动端技术栈，完成问题发送、流式展示、停止生成、错误重试和会话 ID 保存。
- **当日产出/验收**：真实设备或浏览器完成 10 轮问答；流式内容无明显重复、停止操作有效、失败后可恢复。
- **建议时间**：2～2.5 小时。

### 第 25 天：实现引用卡片与原文预览

- **学习目标**：发挥前端/移动端优势，提高可解释性与可验证性。
- **核心知识**：引用与答案映射、折叠展示、来源排序、长文本阅读、无效链接处理。
- **动手任务**：将 API 返回的引用渲染为卡片；支持展开摘要、查看文档名/章节/版本，并对不可访问来源给出提示。
- **当日产出/验收**：桌面和移动尺寸均可用；至少 10 个回答引用能正确显示，重复引用得到合并，空引用不显示伪入口。
- **建议时间**：2 小时。

### 第 26 天：建立反馈闭环

- **学习目标**：将用户体验信号变成可分析的数据。
- **核心知识**：点赞/点踩、原因标签、自由文本、问题升级、隐私、反馈与会话关联。
- **动手任务**：增加回答反馈 UI；定义“不准确、未解决、引用无关、内容过期、体验问题”等标签；调用 Dify 或自有服务保存反馈。
- **当日产出/验收**：反馈可以提交、去重并与消息关联；完成 5 条模拟反馈并能在后台或日志中查询。
- **建议时间**：2 小时。

### 第 27 天：建立基础评测集

- **学习目标**：用固定问题持续比较版本，而不是靠随手提问。
- **核心知识**：代表性样本、黄金答案、预期证据、可回答/不可回答、难度、业务风险分层。
- **动手任务**：从真实文档和第 1 天需求中整理 50 条评测问题，覆盖直接问法、同义问法、多条件问题、版本问题、无答案问题。
- **当日产出/验收**：完成 `eval/rag-eval.csv`；每条包含 question、category、expected_answer_points、expected_source、answerable、risk_level。
- **建议时间**：2～2.5 小时。

### 第 28 天：周末整合——执行首次评测

- **学习目标**：找出问题发生在检索还是生成阶段。
- **核心知识**：检索命中、答案要点覆盖、引用支持度、无依据回答、错误分类；不需要复杂统计或算法实现。
- **动手任务**：运行 50 条评测；人工检查 Top-K 是否出现预期证据、回答是否覆盖关键点、引用是否支持答案；标注失败原因。
- **当日产出/验收**：完成评测报告 v1，给出基线指标和 Top 5 失败类型；每个失败能归类到数据、分段、元数据、召回、Prompt 或流程之一。
- **建议时间**：2.5 小时。

### 第 29 天：根据评测进行一次受控优化

- **学习目标**：一次只改变少量因素，并用同一评测集验证收益。
- **核心知识**：基线对比、避免同时乱调参数、局部优化可能造成其他类别退化。
- **动手任务**：从 Top 5 失败类型选择影响最大的 1～2 个，调整清洗/分段/元数据/检索参数或 Prompt；重新运行相同问题集。
- **当日产出/验收**：完成评测报告 v2；记录改动前后指标、改善案例和退化案例；不能改善时也要写明证据与下一步。
- **建议时间**：2～2.5 小时。

### 第 30 天：项目验收、复盘与第 6 月准备

- **学习目标**：把本月成果整理成作品集，并明确从低代码过渡到代码自建 RAG 的路径。
- **核心知识**：架构表达、技术决策、限制说明、迁移边界；Dify 帮助验证链路，自建用于更强控制和工程集成。
- **动手任务**：完成 README、架构图、3～5 分钟演示视频脚本、部署/配置说明、评测报告和本月复盘；列出下月要用 TypeScript 重写的模块。
- **当日产出/验收**：项目可从需求讲到数据、工作流、客户端和评测；新用户按 README 能完成演示；列出第 6 月 Backlog 与优先级。
- **建议时间**：2～2.5 小时。

## 九、与第 6 月 TypeScript 自建 RAG 的衔接

第 6 月不是推翻本月成果，而是把已验证的业务链路逐步替换为可控制的代码模块：

| 本月 Dify 能力 | 第 6 月 TypeScript 实现 | 需要保留的资产 |
|---|---|---|
| 文档导入与解析 | Node.js 文档处理管线 | 原始/清洗文档与数据清单 |
| 自动分段 | 可配置 Chunk 策略 | 分段实验与决策记录 |
| Embedding 与索引 | Embedding API + PostgreSQL/pgvector | 选型约束与元数据字典 |
| 知识检索节点 | TypeScript 检索服务 | 50 条评测问题与基线指标 |
| Chatflow 条件分支 | LangGraph.js 或普通状态工作流 | 流程图、节点输入输出契约 |
| Dify 应用 API | 自有 Fastify/NestJS API | 客户端交互和错误状态设计 |
| 引用与反馈 | 自有 citation/feedback 数据模型 | 引用 UI、反馈标签和真实样本 |

下月开始前应准备好：

- 最终清洗文档与元数据 CSV。
- 50 条以上固定评测问题及预期证据。
- Dify 基线结果、配置截图和已知缺陷。
- 一份清晰的数据流图与 API 输出结构。
- 第 6 月优先级：先实现最小检索链路，再做引用、过滤和评测，不一次性重写所有能力。

> 本月不安排算法题、模型训练或复杂数学。评价学习效果的标准，是能否根据业务需求搭建、调试、集成并评测一个可信的知识助手。
