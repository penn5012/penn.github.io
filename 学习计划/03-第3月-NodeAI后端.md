# 第 3 月：Node.js + TypeScript AI 后端

> 适用背景：已有前端或移动端开发经验，已完成一个具备流式输出、多轮对话和本地历史记录的 AI 聊天界面。
> 本月主线：TypeScript + Fastify。
> 学习节奏：工作日每天 1.5～2.5 小时；每 6～7 天安排一次整合、回归或复盘。
> 核心原则：不刷算法题，不学习模型训练，用工程项目带动知识学习。

## 1. 本月定位

前两个月的重点是 AI 客户端与交互体验，本月要跨过“只会在客户端调用模型 API”这道门槛，把聊天应用改造成真正的前后端系统。

你不需要先成为传统后端专家。本月只学习 AI 应用最常用的后端能力：安全代理模型请求、设计聊天 API、流式转发、持久化数据、身份认证、错误恢复、测试、限流和容器化。已有的 TypeScript、异步编程、HTTP 请求、状态管理和客户端调试经验都可以直接复用。

## 2. 前置条件

- 能使用 TypeScript 编写前端或移动端业务代码。
- 理解 `Promise`、`async/await`、JSON 和 HTTP 基础概念。
- 已有一个可运行的 AI 聊天客户端；没有现成项目时，可用最简单的网页聊天界面替代。
- 本机已安装 Node.js LTS、npm/pnpm、Git 和 Docker Desktop。
- 准备一个模型服务 API Key；任何 Key 都只能放在服务端环境变量中。
- 不要求掌握 Python，本月测试统一使用 Vitest。

## 3. 本月学习目标

完成本月后，你应该能够：

1. 使用 Fastify + TypeScript 搭建分层的 REST API 服务。
2. 通过服务端安全调用模型，客户端不再持有模型 API Key。
3. 使用 SSE 把模型增量内容流式转发给 Web 或移动客户端。
4. 使用 PostgreSQL + Prisma 设计并持久化用户、会话、消息数据。
5. 使用 JWT 完成注册、登录、接口鉴权和资源归属校验。
6. 建立统一错误响应、结构化日志、请求 ID 和基础审计信息。
7. 为核心服务编写 Vitest 单元测试和接口集成测试。
8. 为模型调用增加输入限制、超时、重试、限流和取消机制。
9. 使用 Docker Compose 启动 API 和 PostgreSQL，并完成端到端验收。

## 4. 固定技术栈

| 层次 | 本月选择 | 用途 |
|---|---|---|
| 运行时 | Node.js LTS | 服务端 JavaScript 运行环境 |
| 语言 | TypeScript | 与现有前端技术栈衔接 |
| Web 框架 | Fastify | REST、插件、Schema 校验、流式响应 |
| 参数校验 | TypeBox + Fastify Schema | 请求与响应的运行时校验 |
| 数据库 | PostgreSQL | 用户、会话、消息等关系数据 |
| ORM | Prisma | Schema、迁移和类型安全查询 |
| 身份认证 | `@fastify/jwt` + `argon2` | JWT 与密码哈希 |
| 模型接入 | 模型厂商官方 Node.js SDK | 服务端模型代理和流式调用 |
| 日志 | Fastify 内置 Pino | 结构化日志和请求追踪 |
| 测试 | Vitest + Fastify `inject` | 单元测试与接口测试 |
| 限流 | `@fastify/rate-limit` | 防滥用和成本控制 |
| 容器 | Docker + Docker Compose | 一致化运行和部署 |

## 5. 最终项目

### 项目名称

**AI Chat Server：支持鉴权、持久化与流式响应的聊天后端**

### 最终业务链路

```text
Web / 移动客户端
  → 注册或登录
  → 携带 JWT 创建会话
  → 发送消息
  → 服务端校验参数与资源归属
  → 保存用户消息
  → 服务端调用模型并通过 SSE 转发增量内容
  → 保存助手完整消息与用量信息
  → 客户端刷新后重新加载会话历史
```

### 建议目录结构

```text
src/
├── app.ts
├── server.ts
├── config/
├── plugins/
├── modules/
│   ├── auth/
│   ├── conversations/
│   ├── messages/
│   └── chat/
├── providers/
│   └── llm/
├── shared/
│   ├── errors/
│   └── observability/
└── tests/
prisma/
├── schema.prisma
└── migrations/
```

## 6. 30 天逐日计划

### 第 1 天：确认架构与建立后端项目

- **学习目标**：理解客户端直连模型的安全问题，明确本月前后端边界。
- **核心知识**：API Key 泄露风险；客户端、业务后端、模型服务三层结构；Fastify 实例与插件概念。
- **动手任务**：画出当前聊天应用的请求链路和目标链路；创建独立后端目录；初始化 TypeScript、Fastify、开发热更新与基础脚本；实现 `GET /health`。
- **当日产出/验收**：运行 `dev` 脚本后访问 `/health` 返回包含 `status: "ok"` 的 JSON；提交一张架构草图和首个 Git commit。
- **建议时间**：2 小时。

### 第 2 天：TypeScript 服务端配置

- **学习目标**：把前端 TypeScript 经验迁移到 Node.js 服务端。
- **核心知识**：ESM、`tsconfig`、Node 类型、源码目录与构建目录、开发模式和生产模式差异。
- **动手任务**：完善 `tsconfig.json`；配置 `dev`、`build`、`start`、`typecheck` 脚本；拆分 `buildApp()` 和 `server.ts`，避免测试时自动监听端口。
- **当日产出/验收**：`typecheck` 与 `build` 均通过；构建产物可以通过生产启动命令运行；`app.ts` 不包含硬编码端口。
- **建议时间**：1.5～2 小时。

### 第 3 天：环境变量与配置校验

- **学习目标**：安全管理模型 Key、数据库地址和运行参数。
- **核心知识**：`process.env`、`.env`、配置分环境、启动时校验、秘密信息不可进入客户端包或 Git。
- **动手任务**：建立配置模块；定义 `PORT`、`HOST`、`DATABASE_URL`、`JWT_SECRET`、`LLM_API_KEY`、`LLM_MODEL`、`LLM_TIMEOUT_MS`；创建不含秘密的 `.env.example`；检查 `.gitignore`。
- **当日产出/验收**：缺少必要变量时进程以明确错误退出；日志不会输出 Key；仓库搜索不到真实 Key。
- **建议时间**：1.5～2 小时。

### 第 4 天：REST 路由和 Schema 校验

- **学习目标**：设计稳定、可校验的业务 API。
- **核心知识**：资源式 URL、HTTP 方法与状态码、请求参数、TypeBox Schema、错误响应结构。
- **动手任务**：先用内存数据实现 `POST /api/conversations`、`GET /api/conversations`、`GET /api/conversations/:id`；为 body、params 和 response 添加 Schema。
- **当日产出/验收**：合法请求返回正确状态码；缺少标题、非法 ID 或超长字段会收到一致的 4xx 响应；使用 REST Client/curl 保存三条可复现请求。
- **建议时间**：2～2.5 小时。

### 第 5 天：服务端模型代理

- **学习目标**：将模型调用从客户端迁移到后端。
- **核心知识**：模型 SDK 初始化；服务端系统提示词；输入白名单；模型响应到业务响应的适配层。
- **动手任务**：建立 `LlmProvider` 接口和厂商 SDK 实现；创建非流式 `POST /api/chat/completions`；限制消息角色、消息数量和单条长度；客户端改为请求本地后端。
- **当日产出/验收**：聊天客户端能通过后端获得模型回答；浏览器网络面板和应用包中均看不到模型 API Key；路由代码不直接依赖具体厂商 SDK。
- **建议时间**：2～2.5 小时。

### 第 6 天：SSE 流式转发

- **学习目标**：掌握从模型到客户端的完整流式链路。
- **核心知识**：SSE 响应头、`data:` 事件格式、增量 token、结束事件、心跳与代理缓冲概念。
- **动手任务**：实现 `POST /api/chat/stream`；把模型流转换为 `delta`、`done`、`error` 三类事件；客户端逐段渲染内容；保留非流式接口便于调试。
- **当日产出/验收**：首段内容无需等待完整回答即可显示；结束时收到明确 `done` 事件；中文和代码块不会因分块而出现乱码。
- **建议时间**：2.5 小时。

### 第 7 天：第一周整合与回归

- **学习目标**：把零散功能整理为清晰的最小 AI 后端。
- **核心知识**：路由、服务、Provider 分层；依赖方向；接口契约；冒烟测试清单。
- **动手任务**：重构目录；清除路由中的模型 SDK 细节；为健康检查、非流式聊天、流式聊天各写一份手工验收步骤；更新 README 的启动方式和环境变量说明。
- **当日产出/验收**：新环境按照 README 可在 10 分钟内启动；客户端聊天、错误提示和停止生成路径均可操作；本周待办全部关闭或记录原因。
- **建议时间**：2～2.5 小时，周末整合。

### 第 8 天：PostgreSQL 与关系数据基础

- **学习目标**：理解聊天数据为什么适合关系数据库。
- **核心知识**：表、行、主键、外键、唯一约束、索引、事务；PostgreSQL 连接字符串。
- **动手任务**：通过 Docker 启动本地 PostgreSQL；使用数据库客户端连接；手工建立一张练习表，完成插入、查询、更新、删除后再删除练习表。
- **当日产出/验收**：能解释用户、会话、消息之间的一对多关系；能执行基础 SQL；数据库数据在容器重启后仍存在。
- **建议时间**：1.5～2 小时。

### 第 9 天：Prisma 初始化和首次迁移

- **学习目标**：使用 ORM 管理类型安全的数据模型与迁移。
- **核心知识**：Prisma Schema、Client、Migration；开发迁移与生产迁移的区别。
- **动手任务**：安装并初始化 Prisma；建立 `User`、`Conversation`、`Message` 模型；增加创建时间、更新时间、消息角色、内容和排序所需索引；执行首次迁移。
- **当日产出/验收**：数据库中存在三张业务表及外键；Prisma Client 正常生成；迁移文件进入 Git，数据库密码没有进入 Git。
- **建议时间**：2～2.5 小时。

### 第 10 天：设计用户、会话、消息模型

- **学习目标**：让数据模型能支持真实的多轮对话。
- **核心知识**：资源归属、级联删除、软删除取舍、消息角色枚举、模型信息、token 用量和错误状态。
- **动手任务**：审查并完善 Prisma 模型；为会话增加标题与可选归档状态；为消息增加 `role`、`status`、`model`、输入/输出 token 等可选字段；写一份模型设计说明。
- **当日产出/验收**：能够回答“删除用户/会话会发生什么”“失败的助手消息如何记录”“历史消息如何稳定排序”；新迁移执行成功。
- **建议时间**：2 小时。

### 第 11 天：数据库插件与 Repository

- **学习目标**：避免业务路由直接散落数据库查询。
- **核心知识**：Fastify 插件；单例数据库连接；Repository 职责；连接释放。
- **动手任务**：把 Prisma 注册为 Fastify 插件；实现 ConversationRepository 和 MessageRepository；用脚本或临时路由写入一组用户、会话和消息种子数据。
- **当日产出/验收**：启动时连接数据库，关闭服务时断开；Repository 可独立被服务层调用；数据库中可查询到完整关系数据。
- **建议时间**：2～2.5 小时。

### 第 12 天：会话 CRUD 持久化

- **学习目标**：用真实数据库替换内存数据。
- **核心知识**：分页、游标或页码、稳定排序、404 与空列表区别、资源更新。
- **动手任务**：实现创建、列表、详情、改名、归档/删除会话接口；列表按更新时间倒序并限制每页数量；暂用开发用户 ID，待 JWT 完成后替换。
- **当日产出/验收**：服务重启后会话仍存在；分页不重复、不遗漏；访问不存在的会话返回结构化 404。
- **建议时间**：2～2.5 小时。

### 第 13 天：消息持久化与事务边界

- **学习目标**：完整保存用户输入和模型输出。
- **核心知识**：先保存用户消息再请求模型；助手消息生成中/完成/失败状态；事务的适用边界。
- **动手任务**：发送消息时创建用户消息；创建 `streaming` 状态的助手消息；流结束后更新完整内容和 `completed` 状态；异常时标记 `failed`；实现会话消息列表接口。
- **当日产出/验收**：刷新客户端仍可恢复对话；模型失败不会丢失用户问题；消息顺序稳定；数据库中没有半条无状态记录。
- **建议时间**：2.5 小时。

### 第 14 天：第二周端到端整合

- **学习目标**：打通数据库、API、模型和客户端。
- **核心知识**：端到端数据一致性；客户端服务端 ID 映射；刷新恢复；重复提交风险。
- **动手任务**：客户端接入会话列表、创建会话、加载历史和发送消息接口；移除客户端本地历史作为主数据源；测试服务/数据库重启、页面刷新和网络中断。
- **当日产出/验收**：注册功能尚未完成也可使用固定开发用户完成全部聊天流程；刷新后会话与消息完整；列出至少 5 个发现的问题及处理结果。
- **建议时间**：2～2.5 小时，周末整合。

### 第 15 天：密码安全与注册接口

- **学习目标**：安全存储账号密码并创建用户。
- **核心知识**：明文密码风险；哈希与加密的区别；salt；Argon2；邮箱标准化；唯一约束。
- **动手任务**：实现 `POST /api/auth/register`；校验邮箱和密码强度；用 Argon2 哈希密码；处理邮箱重复错误；响应中永不返回密码哈希。
- **当日产出/验收**：数据库只保存不可逆哈希；重复邮箱返回明确 409；日志、响应和测试快照均不包含密码。
- **建议时间**：2 小时。

### 第 16 天：登录和 JWT

- **学习目标**：完成无状态身份认证的最小闭环。
- **核心知识**：JWT header/payload/signature；签发与验证；过期时间；Bearer Token；JWT 不能存放秘密信息。
- **动手任务**：实现 `POST /api/auth/login`；验证密码后签发短时访问令牌；建立鉴权钩子；实现 `GET /api/me`；客户端保存并携带 token。
- **当日产出/验收**：正确凭据可访问 `/api/me`；错误密码、缺少 token、伪造 token、过期 token 均返回 401；响应不泄露具体认证细节。
- **建议时间**：2～2.5 小时。

### 第 17 天：资源归属与越权防护

- **学习目标**：确保用户只能操作自己的数据。
- **核心知识**：认证与授权的区别；对象级授权；IDOR 越权风险；查询条件必须包含用户 ID。
- **动手任务**：移除固定开发用户；所有会话与消息查询都从 JWT 获取用户 ID；创建两个测试用户；验证跨用户读取、更新、删除、发消息全部失败。
- **当日产出/验收**：用户 A 无法通过猜测 UUID 访问用户 B 的会话；Repository/Service 查询明确包含所有者条件；越权行为有安全日志但不泄露资源存在性。
- **建议时间**：2～2.5 小时。

### 第 18 天：统一错误处理

- **学习目标**：让客户端能够稳定识别并展示错误。
- **核心知识**：业务错误与系统错误；错误码、HTTP 状态码、用户消息；异常栈仅留服务端；关联请求 ID。
- **动手任务**：建立 `AppError` 和错误码；统一处理校验、认证、资源不存在、限流、模型超时和未知异常；客户端按错误码显示重试、重新登录或普通提示。
- **当日产出/验收**：所有错误响应至少包含 `code`、`message`、`requestId`；未知异常返回 500 且不返回堆栈；服务端日志可通过 requestId 找到详细错误。
- **建议时间**：2 小时。

### 第 19 天：Pino 结构化日志与请求追踪

- **学习目标**：从“看 console.log”升级到可检索的服务日志。
- **核心知识**：JSON 日志；日志级别；请求 ID；耗时；敏感字段脱敏；业务事件和技术日志。
- **动手任务**：配置开发友好和生产 JSON 两种输出；记录请求入口/结束、用户 ID、会话 ID、模型名、耗时和状态；为 authorization、password、API Key 配置脱敏。
- **当日产出/验收**：一次聊天请求可用 requestId 串起 HTTP、数据库和模型日志；日志不含 token、密码、完整 Key 或完整私聊正文。
- **建议时间**：2 小时。

### 第 20 天：Vitest 与可测试架构

- **学习目标**：为关键逻辑建立快速单元测试。
- **核心知识**：测试金字塔；Arrange-Act-Assert；依赖注入；Mock 外部模型而非真实计费调用。
- **动手任务**：配置 Vitest；为配置校验、密码服务、模型响应适配和 ConversationService 编写单元测试；使用假的 LlmProvider 模拟成功、超时和异常。
- **当日产出/验收**：测试不联网、不调用真实模型、不依赖启动端口；核心成功与失败分支至少各有一个测试；`npm test`/`pnpm test` 一次通过。
- **建议时间**：2～2.5 小时。

### 第 21 天：接口集成测试与第三周回归

- **学习目标**：验证路由、鉴权、校验和服务层能够协同工作。
- **核心知识**：Fastify `inject`；测试数据库隔离；测试夹具；接口契约；回归测试。
- **动手任务**：为注册、登录、创建会话、列出会话、越权访问和发送消息编写集成测试；统一创建/清理测试数据；运行客户端端到端冒烟测试。
- **当日产出/验收**：至少覆盖一条完整的“注册→登录→会话→消息”链路和主要 4xx 分支；连续运行两次测试结果一致；记录当前覆盖盲区。
- **建议时间**：2.5 小时，周末整合。

### 第 22 天：模型调用超时与取消

- **学习目标**：避免模型请求无限占用连接和费用。
- **核心知识**：`AbortController`；服务端超时；客户端断开；SSE 清理；请求生命周期。
- **动手任务**：为模型 SDK 调用设置可配置超时；客户端点击停止时中止请求；服务端检测连接关闭并取消上游模型流；超时后标记助手消息为失败。
- **当日产出/验收**：人为设置极短超时可得到可识别错误；点击停止后模型流不再继续；监听器和计时器被清理；日志记录实际耗时和取消原因。
- **建议时间**：2～2.5 小时。

### 第 23 天：安全重试策略

- **学习目标**：只对适合的瞬时故障进行有限重试。
- **核心知识**：指数退避与抖动；可重试状态码；4xx 不重试；流式输出开始后不盲目重试；重试预算。
- **动手任务**：在 LlmProvider 外建立重试包装；仅对连接错误、429 和部分 5xx 重试；最多重试 2 次；记录 attempt；为重试成功和最终失败编写 Vitest 测试。
- **当日产出/验收**：模拟第一次 429、第二次成功时只产生一条业务消息；认证错误不重试；已经向客户端发送 delta 后不会偷偷从头再答。
- **建议时间**：2 小时。

### 第 24 天：限流、输入边界与成本保护

- **学习目标**：控制接口滥用和不可预测的模型费用。
- **核心知识**：IP 限流与用户级限流；速率窗口；消息长度、历史轮数和并发限制；429 与 `Retry-After`。
- **动手任务**：接入 `@fastify/rate-limit`；登录接口按 IP 限流、聊天接口按用户限流；限制消息长度、单次历史条数和用户并发流数量；在客户端展示稍后重试提示。
- **当日产出/验收**：自动连续请求能触发 429；不同用户不会共享同一用户额度；异常大输入在调用模型前被拒绝；限制值可通过环境变量调整。
- **建议时间**：2～2.5 小时。

### 第 25 天：重复请求与幂等性

- **学习目标**：解决移动网络重连或连点造成的重复消息。
- **核心知识**：客户端请求 ID；唯一约束；幂等键；“至少一次”请求带来的重复副作用。
- **动手任务**：客户端每次发送生成 `clientMessageId`；消息表添加对应唯一约束；服务端收到相同用户、会话和 clientMessageId 时返回已有结果或冲突状态；模拟双击和网络重发。
- **当日产出/验收**：同一请求并发发送两次，数据库只出现一条用户消息且只启动一次模型任务；不同请求仍可正常发送。
- **建议时间**：2～2.5 小时。

### 第 26 天：健康检查与优雅停机

- **学习目标**：让服务具备可部署、可运维的基本行为。
- **核心知识**：liveness 与 readiness；数据库依赖检查；SIGTERM；停止接收新请求；资源释放。
- **动手任务**：拆分 `/health/live` 和 `/health/ready`；readiness 检查数据库；捕获终止信号并关闭 Fastify 与 Prisma；模拟数据库不可用和服务停止。
- **当日产出/验收**：进程存活但数据库不可用时 live 成功、ready 失败；终止服务不出现未处理 Promise；日志明确记录启动和停机阶段。
- **建议时间**：1.5～2 小时。

### 第 27 天：编写 Dockerfile

- **学习目标**：把 API 服务构建为可复现镜像。
- **核心知识**：镜像层、构建上下文、多阶段构建、非 root 用户、`.dockerignore`、运行时环境变量。
- **动手任务**：编写多阶段 Dockerfile；只把生产需要的文件放进最终镜像；配置非 root 运行；加入 `.dockerignore`；构建并单独运行 API 镜像。
- **当日产出/验收**：镜像能启动且 `/health/live` 正常；镜像内不含 `.env`、Git 历史和开发缓存；容器不是 root 用户运行。
- **建议时间**：2～2.5 小时。

### 第 28 天：Docker Compose 全栈启动

- **学习目标**：用一条命令启动 API 与 PostgreSQL。
- **核心知识**：Compose 服务、网络、命名卷、依赖健康检查、容器内主机名；迁移执行时机。
- **动手任务**：编写 Compose 配置；加入 API、PostgreSQL、数据库健康检查和持久化卷；使用容器服务名配置数据库地址；执行 Prisma migration；从客户端连接容器化 API。
- **当日产出/验收**：一条 Compose 命令可启动完整后端；首次启动能完成迁移；重启容器后数据保留；API 在数据库就绪前不会误报 ready。
- **建议时间**：2.5 小时，周末整合。

### 第 29 天：生产化验收与故障演练

- **学习目标**：用场景而非“能跑起来”判断项目质量。
- **核心知识**：验收清单；故障注入；恢复能力；安全基线；性能与成本观察。
- **动手任务**：依次演练错误 Key、数据库停止、模型超时、重复消息、过长输入、超限请求、JWT 过期、客户端中断；修复阻塞问题；统计一次请求的首 token 延迟、总耗时和模型用量字段。
- **当日产出/验收**：每个故障都有合理状态码、用户提示和可定位日志；服务恢复依赖后无需清库即可继续使用；形成一页故障演练记录。
- **建议时间**：2～2.5 小时。

### 第 30 天：文档、演示与月度复盘

- **学习目标**：把项目整理成可展示的作品，而非只留在本机的练习代码。
- **核心知识**：技术 README；架构决策；API 示例；测试与已知限制；面试中的项目表达。
- **动手任务**：完善 README、环境变量说明、数据模型图、API 列表、启动与测试命令；录制 3～5 分钟演示；清理临时代码和无效日志；完成下方复盘。
- **当日产出/验收**：陌生开发者按 README 可启动项目；演示覆盖登录、创建会话、流式聊天、刷新恢复、停止生成和错误恢复；测试全部通过；本月代码有清晰 Git 历史。
- **建议时间**：2～2.5 小时。

## 9. 与第 4 月 Function Calling 的衔接

本月的 `LlmProvider`、鉴权、会话/消息表、SSE、错误处理和日志，正是下个月 Function Calling 的基础。第 4 月不要重新搭项目，而是在这个服务上继续增加工具系统：

1. 把模型 SDK 的普通消息响应扩展为结构化 tool call 响应。
2. 建立工具注册表，为每个工具定义名称、用途、JSON Schema 和执行函数。
3. 使用 TypeBox/JSON Schema 校验模型产生的工具参数。
4. 为查询型工具接入真实或模拟 API，为写操作增加 JWT 权限与人工确认。
5. 把“模型请求 → 工具调用 → 工具结果 → 模型总结”全过程写入日志和消息记录。
6. 复用本月的超时、重试和限流，但注意创建待办、发消息等有副作用工具必须使用幂等键，不能盲目重试。

进入第 4 月前，最重要的门槛不是代码量，而是能清楚解释：模型只负责**选择工具并生成参数**，真正的工具执行、权限校验和结果持久化始终由后端负责。
