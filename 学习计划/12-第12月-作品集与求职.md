# 第12月：作品集与求职——把项目能力转化为可信的职业证据

> 适用背景：已有前端/移动端工程经验，完成了前11个月 AI 应用开发学习，并已部署“企业售后知识库与工单 Agent”。本月不学习算法题、不训练模型、不补复杂数学；核心任务是把项目做稳、讲清、展示出来，并形成持续求职的闭环。

## 本月定位

第12个月不是继续堆新框架，而是完成从“做过一个 AI Demo”到“能够证明自己胜任 AI 应用工程岗位”的最后一公里。

你的差异化定位应当是：

> 能把前端/移动端交互、TypeScript 全栈工程、RAG 知识库、Agent 工作流和生产化能力连接起来，独立完成从需求分析、方案设计、开发联调、效果评测到部署迭代的 AI 应用工程师。

本月所有材料都围绕两个主作品组织：

1. **企业知识库系统**：突出数据接入、切分、混合检索、重排序、引用、权限、反馈和评测。
2. **企业售后知识库与工单 Agent**：突出状态工作流、工具调用、人工审批、失败恢复、可观测性、安全和用户体验。

其中第二个项目可包含第一个项目的能力，但作品集页面必须能分别讲清“RAG 能力”和“业务 Agent 能力”。

## 前置条件

开始本月前，应具备以下可运行资产：

- 一个 TypeScript 主线的前端或移动端客户端。
- 一个 Node.js/TypeScript AI 后端，能够保护模型密钥并流式返回结果。
- PostgreSQL + pgvector、Redis，以及 Docker Compose 部署配置。
- 已实现文档导入、混合检索、引用回答和基础 RAG 评测。
- 已实现 LangGraph 工作流、工具调用、人工审批、重试与中断恢复。
- 已接入基础日志、Tracing、限流、权限控制和成本统计。
- 至少一套脱敏演示文档、演示账户与可重复执行的演示流程。

如果某项缺失，不回头重新看完整课程，只在第1周的缺口审计中按求职价值和风险优先级补齐。

## 本月目标

完成本月后，你应当能够：

- 用 30 秒、3 分钟和 10 分钟三个版本清楚介绍项目。
- 用需求、架构、数据流、关键决策和指标解释项目，而不是罗列框架名。
- 提供可验证的 RAG 评测报告与 Agent 工作流测试报告。
- 展示真实的异常处理、安全边界、人工审批与恢复机制。
- 让招聘者通过 README、个人站点、演示视频和在线 Demo 快速理解你的能力。
- 针对 AI 应用、AI 全栈、RAG、Agent、AI 产品工程师岗位定制简历。
- 完成非算法类技术面试准备，包括系统设计、RAG/Agent 原理、工程排障和项目讲解。
- 建立岗位筛选、投递、跟进、面试和复盘的可持续流程。

## 本月工作原则

1. **证据优先**：所有“掌握”都要对应代码、文档、测试、指标或可演示行为。
2. **业务优先**：先讲解决了什么问题，再讲使用了什么技术。
3. **可复现优先**：招聘者应能按 README 启动核心服务，或通过视频看见完整流程。
4. **边界清晰**：明确哪些操作由确定性工作流控制，哪些节点允许 Agent 自主决策。
5. **不虚构数据**：指标必须注明数据集规模、环境、模型版本和测试日期。
6. **不暴露秘密**：仓库、截图、日志、视频中不得出现真实 API Key、隐私数据或公司机密。
7. **不刷算法题**：本月面试准备只覆盖与你目标岗位直接相关的应用工程、系统设计和项目表达。

**核心知识**

**动手任务**

**当日产出/验收**

- 项目固定到一个可回退的版本标签。
- 看板中包含本月全部交付项，每项有验收定义。

**当日产出/验收**

**建议时间**：2小时

## 第 3 天：端到端功能与体验审计

**学习目标**

- 从用户和面试官视角发现项目最影响可信度的问题。

**核心知识**

- 演示项目最常见的失败不是“模型不够强”，而是加载状态不清、错误不可恢复、引用打不开、工具重复执行、审批流程中断或移动端适配不完整。

**动手任务**

1. 从注册/登录开始完整走一遍：提问、流式回答、引用查看、工具调用、人工审批、工单创建、历史记录。
2. 测试空输入、超长输入、断网、模型超时、检索无结果、工具失败、重复点击、刷新恢复。
3. 分别检查桌面端和移动端，记录布局、键盘、滚动、加载、错误提示和可访问性问题。
4. 为每个问题记录复现步骤、期望结果、实际结果和优先级。

**当日产出/验收**

- `项目缺口审计.md`，包含功能、体验、性能、安全、文档五类问题。
- 至少完成20个场景检查，P0问题都有负责人和修复日期。

**建议时间**：2小时

## 第 4 天：修复演示链路中的 P0 Bug

**学习目标**

- 确保核心演示流程稳定完成，不因异常状态卡死。

**核心知识**

- AI交互需要显式状态：等待模型、生成中、等待工具、等待审批、成功、失败、可重试。
- 工具写操作必须避免重复执行，并对超时和部分成功提供明确结果。

**动手任务**

1. 修复昨天发现的所有 P0 问题，优先处理崩溃、数据丢失、重复提交和审批失效。
2. 为流式回答增加中断、重试和错误恢复。
3. 为创建工单等写操作增加请求ID或幂等键。
4. 为检索无结果和工具失败设计用户可理解的降级提示。
5. 为核心修复补充自动化测试或最小回归脚本。

**当日产出/验收**

- 核心演示流程连续执行3次均成功。
- P0问题清零，每项都有对应提交与验证记录。
- 写操作重复点击不会产生重复工单。

**建议时间**：2.5小时

## 第 5 天：体验加固与演示模式

**学习目标**

- 发挥前端/移动端背景优势，让AI执行过程清楚、可控、可信。

**核心知识**

- AI UX 的关键不是动画，而是让用户知道系统正在做什么、使用了什么证据、下一步是否需要授权。

**动手任务**

1. 优化流式文本、引用卡片、工具执行进度、审批确认和错误恢复界面。
2. 增加“本次回答依据”区域，显示文档名、片段和相关性信息。
3. 为工具调用展示状态时间线，隐藏不必要的内部推理信息。
4. 增加演示模式：预置问题、示例入口、演示账户说明。
5. 检查移动端触控区域、键盘遮挡、长文本滚动和弱网反馈。

**当日产出/验收**

- 完成一条无讲解也能理解的演示路径。
- 用户可以分辨“检索中、生成中、等待审批、执行成功、执行失败”。
- 引用可以定位原文，敏感内部推理不展示给用户。

**建议时间**：2小时

## 第 8 天：编写产品需求文档

**学习目标**

- 能用业务语言说明为什么要做这个系统，以及成功标准是什么。

**核心知识**

- 一个可信的AI项目需要定义用户、痛点、流程、边界、指标和风险。
- “用了 RAG 和 Agent”不是需求；“缩短售后答复时间并减少无依据回答”才是目标。

**动手任务**

1. 编写背景、目标用户、核心痛点、用户故事和业务流程。
2. 定义功能范围与非目标，说明哪些动作需要人工审批。
3. 定义成功指标：检索命中、回答有据、工具成功、处理时长和用户反馈。
4. 记录关键约束：隐私、权限、成本、延迟和数据更新。

**当日产出/验收**

- `产品需求文档.md`。
- 至少包含3类用户、5条用户故事、业务流程、非目标和可测量指标。

**建议时间**：2小时

**当日产出/验收**

3. 绘制售后状态图：分类、补充信息、检索、生成建议、风险判断、审批、工具执行、结束。

**建议时间**：2小时

## 第 11 天：完成RAG评测数据与实验设计

**学习目标**

- 建立可复现的评测方法，避免用几个“看起来不错”的问题证明效果。

**核心知识**

- 检索和生成要分开评测。
- 评测数据应覆盖直接事实、跨段信息、同义改写、元数据过滤、无答案和越权问题。

**动手任务**

1. 清理或扩展到至少100条脱敏测试问题。
2. 为每条问题标注类型、期望文档、期望要点、是否应拒答。
3. 固定文档版本、模型、Embedding、切分和检索配置。
4. 定义 Recall@5、回答正确率、引用正确率、无依据回答率、延迟和成本的计算口径。

**当日产出/验收**

- 版本化评测集与 `RAG评测方案.md`。
- 每类问题都有样本，指标有清晰定义，评测可重复运行。

**建议时间**：2.5小时

## 第 12 天：执行RAG评测并形成报告

**学习目标**

- 用数据说明系统的优势、边界和下一步优化方向。

**核心知识**

- 报告应同时提供总体指标、分类指标、失败案例和配置说明。
- 不隐藏失败样本，能解释失败原因比单纯报高分更可信。

**动手任务**

1. 运行完整评测并保存原始结果。
2. 汇总检索、答案、引用、拒答、延迟和成本指标。
3. 选择至少5个失败案例，归因为数据、切分、检索、重排、Prompt或权限问题。
4. 选一个低成本改进项进行 A/B 对比，不为了数字临时修改评测集。

**当日产出/验收**

- `RAG评测报告.md`与原始结果文件。
- 报告注明日期、环境、模型、数据集规模、配置、指标和失败分析。
- 至少有一组改进前后对比及合理结论。

**建议时间**：2.5小时

## 第 13 天（周末整合）：Agent工作流测试设计与执行

**学习目标**

- 证明工作流不仅在理想路径上可用，也能处理异常和高风险操作。

**核心知识**

**动手任务**

3. 执行自动化或半自动化测试，保存 Trace ID 和结果。
4. 修复严重路径错误，并重新执行失败场景。

**当日产出/验收**

- `Agent工作流测试报告.md`。
- 核心写操作100%经过审批和权限校验。
- 工作流不存在明显无限循环；失败状态可重试或安全结束。

## 年度总验收

全年 12 个月按每月 30 个学习日编排，共 360 个学习日。自然年剩余的 5 天（闰年为 6 天）作为机动缓冲，只用于休息、补做未完成任务或处理工作突发情况，不新增学习内容；不要为了追赶进度压缩项目验收和复盘。

一年学习结束时，不以“看完多少课程”为标准，而以以下能力进行验收。

### 1. 需求与选型

- 能把模糊业务需求拆成用户、数据、流程、权限、指标和风险。
- 能判断什么时候使用普通代码、确定性 Workflow、RAG、单 Agent 或多 Agent。
- 能解释为什么不把支付、删除、发消息、创建工单等高风险动作完全交给模型。

### 2. AI应用与交互

- 能实现流式聊天、停止生成、重试、历史记录、结构化卡片和错误恢复。
- 能把工具执行状态、引用证据和人工审批清楚呈现给用户。
- Web或移动端在弱网、长内容和异常状态下仍可使用。

### 3. 后端与数据

- 能使用 TypeScript 构建安全的 AI API，保护模型密钥。
- 能使用 PostgreSQL、pgvector、Redis 和 Docker Compose。
- 能实现鉴权、权限、限流、超时、重试、幂等、日志和配置管理。

### 4. 知识库与RAG

- 能完成解析、清洗、切分、向量化、存储、混合检索、重排、引用和增量更新。
- 能实现元数据和用户权限过滤。
- 能使用至少100条代表性问题评测检索与生成，并分析失败原因。

### 5. Agent工作流

- 能使用 LangGraph.js 表达状态、分支、循环、Checkpoint、暂停与恢复。
- 能实现结构化工具调用、参数验证、权限控制、人工审批和失败恢复。
- 能解释 ReAct、Planning、Memory、MCP 的用途与边界，不为了“像Agent”而增加不可控性。

### 6. 生产化与安全

- 能部署服务并使用健康检查、日志、Trace、成本和延迟指标排障。
- 能处理 Prompt Injection、越权检索、工具注入、秘密泄漏和日志隐私风险。
- 能明确演示方案与真正生产环境之间仍存在的差距。

### 7. 作品与表达

- 至少有两个清晰定位的项目案例，或一个覆盖RAG与Agent的主项目加一个独立前端/移动端AI体验项目。
- 每个主项目具有 README、架构图、需求文档、API文档、部署文档、测试/评测报告和演示视频。
- 能完成30秒自我介绍、3分钟项目介绍、10分钟深挖和一道AI应用系统设计。

### 8. 求职闭环

- 有明确的岗位筛选规则，不投算法训练类岗位。
- 有基础简历、定制版本、投递追踪和面试复盘机制。
- 每次面试后能把反馈转换成文档、实验、项目或表达上的具体改进。

## 未来90天后续路线

### 第31—60天：扩大真实反馈

- 每周定制投递10—15个高匹配岗位，避免无差别海投。
- 每周完成一次模拟面试或真实面试复盘。
- 邀请5—10名真实用户试用项目，记录失败案例和体验反馈。
- 优先修复影响可信度的问题，不为追热点随意换框架。
- 尝试为一个开源AI应用项目修复文档、前端体验、TypeScript SDK或测试问题。

### 第61—90天：强化一个岗位方向

根据市场反馈选择一条主线：

- **AI全栈方向**：强化鉴权、多租户、后台任务、部署、监控和端到端交付。
- **RAG方向**：强化复杂文档、混合检索、权限检索、评测和数据更新。
- **Agent方向**：强化状态持久化、工具安全、审批、恢复、Trace和工作流评测。
- **AI产品工程方向**：强化交互、需求验证、用户反馈、实验和指标闭环。

只选一条作为主线，其余保持能协作和能解释的水平。

### 第91—120天：争取真实交付证据

- 完成一个真实客户、朋友团队、社区或开源项目中的小型AI需求。
- 把真实约束、迭代过程和结果写成新的项目案例。
- 根据实际面试数据调整简历和岗位范围。
- 如果回复率低，先检查岗位匹配和简历首屏；如果能进面但不过，优先修正项目深挖、系统设计和沟通表达。

## 每周持续节奏建议

- 2小时：岗位筛选与定制投递。
- 2小时：非算法面试与系统设计练习。
- 2小时：项目维护和真实反馈修复。
- 1小时：文档、作品集和个人站点更新。
- 1小时：面试复盘与下一周调整。

最终目标不是把自己包装成算法工程师，而是让招聘者清楚看到：你能利用已有的前端/移动端优势，独立把一个 AI 需求做成可用、可控、可评测、可部署、可持续改进的产品。
