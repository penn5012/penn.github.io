| 2027-04-07 | Day 240 | 第30天 | [最终验收、复盘与第 9 月衔接](2027-04/2027-04-07-Day240-最终验收-复盘与第-9-月衔接/README.md) | 2.5 小时。  ---  ## 月末项目验收清单  ### 功能  - [ ] 支持“分类 → 澄清 → RAG → 方案 → 风险判断 → 审批 → 创建工单 → 通知”完整链路。 - [ ] 澄清流程最多循环 3 次，超过上限自动转人工。 - [ ] RAG 回答带有效引用，无证据时不会编造方案。 - [ ] 中高风险操作必须经过具有权限的人员审批。 - [ ] 用户补充信息和审批后均可从 Checkpoint 恢复。 - [ ] 工单创建具备幂等性，重复恢复不会重复建单。 - [ ] 通知失败可重试或进入待补发状态，不破坏工单数据。  ### 工程质量  - [ ] 每个外部调用都有超时、有限重试和清晰错误分类。 - [ ] 关键节点有单元测试，至少 8 条主流程/异常流程集成测试。 - [ ] 每次运行都有 Trace、结构化日志和关联 ID。 - [ ] 日志、事件和模型上下文经过隐私脱敏。 - [ ] Web/移动端可显示实时进度、证据、澄清、审批和失败状态。 - [ ] 项目可通过 Docker Compose 或明确脚本在新环境启动。  ### 可量化结果  - [ ] 使用至少 20 个售后案例完成端到端验收。 - [ ] 记录流程成功率、人工介入率、平均/P95 延迟和工具调用成功率。 - [ ] 重复提交测试中，重复工单数量为 0。 - [ ] 高风险未审批直接执行的数量为 0。 - [ ] 每个失败案例都能通过 Trace 定位到具体节点。  ## 月末复盘模板  1. 哪些步骤最初想交给模型，最后为什么改为规则或人工判断？ 2. 状态 Schema 哪些字段发生过变化，变化暴露了什么需求问题？ 3. 哪种故障最容易造成重复副作用，最终如何用幂等和 Checkpoint 解决？ 4. 哪条分支的用户体验最差，前端如何呈现等待、失败和恢复？ 5. 本月 20 个案例中最常见的失败类型是什么？下月如何用数据改进？ 6. 哪些节点具有“任务路径无法预先枚举、需动态选择工具”的特征，适合在第 9 月引入 Agent？  ## 与第 9 月 Agent / MCP 的衔接  下月不要推翻本月状态图，而是在可控框架内做局部升级：  - 将“复杂问题诊断”升级为受限 Agent，让它在知识检索、账户查询、设备诊断等只读工具中动态选择。 - 用 MCP 标准化接入知识库、订单查询和工单系统，但服务端仍执行身份校验、参数校验和权限控制。 - 为 Agent 增加最大步数、允许工具列表、成本预算、超时和 Trace。 - 保留 LangGraph 作为外层编排器，继续负责审批、Checkpoint、重试、幂等、补偿和最终状态。 - 创建工单、发通知、修改账户等写操作仍通过确定性节点，并在高风险场景保留人工审批。  完成本月后，你的核心成果不是“会调用 LangGraph API”，而是能把一个包含 LLM 不确定性和真实业务副作用的需求，设计成可暂停、可恢复、可测试、可观测、对用户友好的生产型工作流。 |
