## 核心知识

- 岗位描述中的“熟悉”要翻译成可证明的行为，例如“熟悉 RAG”应对应切分策略、混合检索、评测指标和排障案例。
- 学历和年限属于筛选条件；项目证据、岗位匹配度和沟通能力是可以主动增强的部分。

### 今日必须回答的问题

1. 用可验证的项目、评测和部署证据证明你能把AI需求做成产品，而不是包装成算法工程师。

## 动手任务

1. 收集15—20个目标岗位描述，按岗位类型标记。
2. 提取高频关键词：TypeScript/Python、API、RAG、LangGraph、Function Calling、MCP、评测、Docker、数据库、监控等。
3. 创建能力矩阵，列出“岗位要求、已有证据、缺口、补齐成本、是否本月处理”。
4. 将缺口分为 P0（阻碍演示）、P1（影响可信度）、P2（加分项）。

### 推荐执行顺序

1. **建立基线**：先运行当前项目并保存改动前的结果。
2. **最小实现**：只实现今天最核心的一条成功路径。
3. **失败路径**：主动制造空输入、超时、错误数据或无权限中的至少一种情况。
4. **补充测试**：为核心逻辑添加自动化测试；无法自动化时写清人工步骤。
5. **联调体验**：检查加载、成功、失败、取消或重试等用户可见状态。
6. **保存证据**：保留命令输出、测试报告、截图、Trace或评测记录。
7. **小步提交**：提交信息只描述今天完成的能力，不写“update”或“fix stuff”。

## 排错顺序

1. 先把问题缩小为稳定可复现的最小样例。
2. 确认输入、配置、网络、依赖服务和数据状态是否与预期一致。
3. 每项简历描述都链接到可验证证据。
4. 演示失败时准备录屏、截图和离线数据降级。
5. 根据真实投递数据调整岗位和表达，不凭感觉改简历。
6. 修复后重新运行原失败样例和一条正常回归样例。
