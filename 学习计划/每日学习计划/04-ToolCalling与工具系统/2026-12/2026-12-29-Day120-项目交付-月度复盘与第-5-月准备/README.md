## 七、本月项目验收清单

### 7.1 功能验收

- [ ] 支持至少 3 个只读工具和 2 个写工具；
- [ ] 支持模型选择工具、提取参数、接收结果并生成最终回答；
- [ ] 支持连续多步工具调用，并有最大轮数和总超时；
- [ ] 参数经过运行时 Schema 校验和业务规则校验；
- [ ] 查询结果来自真实数据库或明确标注的 Mock 数据；
- [ ] 创建待办和创建工单都必须人工确认；
- [ ] 确认请求支持取消、过期和刷新恢复；
- [ ] 写操作支持幂等，重复确认不会重复创建；
- [ ] Web 或移动端具有工具状态卡片和确认卡片；
- [ ] 工具结果、错误和数据来源能被用户理解。

### 7.2 安全与工程验收

- [ ] 模型不能传入或覆盖 `userId`、`tenantId` 等可信身份字段；
- [ ] 模型只能调用注册表白名单中的工具；
- [ ] 工具可见性和执行时都进行权限检查；
- [ ] 不接受模型生成的任意 SQL、URL、命令或代码执行；
- [ ] 每个工具都有超时，重试次数有上限；
- [ ] 未做幂等保护的写操作不会自动重试；
- [ ] 工具循环有轮数、调用数和总时间上限；
- [ ] 审计日志能关联用户、会话、工具、审批与业务结果；
- [ ] 日志和模型上下文中不暴露密钥与敏感字段；
- [ ] 关键单元、集成和端到端测试可以一条命令运行。

### 7.3 量化验收

- [ ] 评测集不少于 30 条；
- [ ] 写操作未确认执行次数为 0；
- [ ] 越权测试成功访问次数为 0；
- [ ] 重复确认导致的重复记录数为 0；
- [ ] 工具选择准确率达到 85% 以上；
- [ ] 关键参数准确率达到 90% 以上；
- [ ] 非超时工具调用成功率达到 95% 以上；
- [ ] 能统计每个工具的 P50/P95 延迟与错误分布。

这些指标用于发现薄弱环节，不需要为了追求数字而修改测试集。失败样例应保留下来，作为第 9～10 月 Agent 评测与生产化工作的初始数据。

## 八、月末复盘模板

在第 30 天按以下问题写一页复盘：

1. 哪三个场景必须使用工具，哪三个场景只需结构化输出？
2. 哪一次失败证明了“模型参数必须校验”？
3. 工具描述中哪处修改最明显改善了选择或参数准确率？
4. 哪些错误可以重试，哪些错误绝不能自动重试？
5. 当前幂等设计如何处理“服务端已成功但客户端超时”？
6. 如果模型请求越权工具，系统有哪几层防线？
7. 用户在确认卡片上是否能清楚判断操作后果？
8. 审计日志是否能从一次投诉反查到完整执行过程？
9. 哪些模块可以直接复用于下月知识库工具？
10. 如果把模型供应商替换掉，哪些业务代码无需修改？

## 九、与第 5 月 Dify 知识库的衔接

第 5 月将进入可视化知识库和基础 RAG。本月不要提前深挖向量算法，只需做好接口衔接：

```ts
type SearchKnowledgeInput = {
  query: string;
  filters?: {
    product?: string;
    version?: string;
    documentType?: string;
  };
  topK?: number;
};

type KnowledgeHit = {
  content: string;
  sourceId: string;
  sourceTitle: string;
  locator?: string;
  score?: number;
  metadata?: Record<string, string>;
};
```

下月可以先让 Dify 承担文档导入、切分、向量化和检索，再通过一个只读 `search_knowledge` 工具把检索结果接入本月的 Tool Registry。这样你会清楚看到：

- Dify 负责知识处理和检索；
- 工具系统负责校验、权限、超时、结果协议和审计；
- LLM 负责结合问题与证据组织回答；
- 前端/移动端负责展示答案、引用、来源和反馈。

进入第 5 月前，确保 `search_knowledge` 的结果中保留来源字段。知识库回答如果没有来源，后续很难做引用展示和正确性评测。
