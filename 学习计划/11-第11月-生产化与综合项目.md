# 第 11 月：AI 应用生产化与综合项目交付

## 本月定位

本月不再增加新的 Agent 框架，而是把前面完成的 RAG 知识库、LangGraph 工作流、工具调用、MCP/n8n 集成和 Web/移动端界面收束成一个**可部署、可观测、可回归、可恢复、可安全操作**的生产版本。

主线仍是 TypeScript，Python 只用于已有文档处理脚本或评测辅助。本月不安排算法题、模型训练和复杂数学。你的前端/移动端背景会用于解决 AI 产品真正棘手的体验问题：流式断线恢复、长任务进度、引用定位、工具审批、失败重试、跨端状态一致性和错误降级。

本月的核心判断标准不是“本地能跑”，而是：

> 当模型变慢、检索失败、用户重复提交、服务重启、输入包含恶意指令或数据库需要恢复时，系统仍然有明确、可验证的行为。

## 前置能力

- 能使用 TypeScript、Node.js、Fastify 或 NestJS 开发 API，并处理 SSE/流式响应。
- 已有一个支持文档入库、混合检索、重排序、引用和评测的 RAG 服务。
- 已用 LangGraph.js 实现状态、条件分支、Checkpoint、人工审批和工具调用。
- 理解单 Agent 与确定性工作流的边界，关键副作用操作不由模型直接执行。
- 已接入 PostgreSQL/pgvector，了解 Redis、Docker Compose 和环境变量。
- 能在 Web 或移动端展示对话、引用、工具调用进度和审批状态。
- 已用 n8n 或类似工具完成至少一条外部业务自动化流程。

如果某一项仍不稳定，只补综合项目直接需要的功能，不暂停一个月重学完整课程。

## 本月目标

完成本月后，你应该能够：

1. 用 Docker Compose 编排 API、Worker、PostgreSQL/pgvector、Redis 和前端服务，并配置健康检查。
2. 区分开发、测试、预发布和生产环境，安全管理密钥、配置与数据库迁移。
3. 为 API、RAG、Agent、工具调用和后台任务建立统一日志、Trace 和 Metrics。
4. 对 Prompt、检索配置和 LangGraph 工作流进行版本化、灰度和回滚。
5. 建立单元、集成、契约、端到端和 AI 回归测试，阻止效果退化进入发布版本。
6. 处理并发、限流、缓存、超时、重试、熔断、幂等、任务恢复和优雅降级。
7. 防御 Prompt Injection，落实数据脱敏、最小工具权限、人工审批和审计。
8. 完成数据库与知识库的备份恢复演练，并搭建基础 CI/CD 流程。
9. 用 P95 延迟、错误率、检索质量、Agent 成功率和单次成本衡量系统表现。
10. 交付可供作品集展示的“企业售后知识库与工单 Agent”生产候选版本。

## 推荐技术栈

- **运行时与语言**：Node.js 20+、TypeScript
- **服务端**：Fastify 或 NestJS，沿用现有项目，不在本月换框架
- **工作流**：LangGraph.js；n8n 用于外部通知或业务自动化
- **数据层**：PostgreSQL + pgvector、Redis
- **任务处理**：BullMQ 或现有队列方案；重点理解任务状态、重试和幂等
- **校验与测试**：Zod、Vitest、Supertest、Playwright
- **可观测性**：结构化日志、OpenTelemetry；可搭配已有 Trace/指标平台
- **性能测试**：k6 或 Artillery，二选一
- **容器与交付**：Docker、Docker Compose、GitHub Actions
- **客户端**：现有 React/Vue/Flutter/原生移动端栈
- **模型与 Embedding**：延续前月适配层，至少保留主模型与降级模型配置

## 月度综合项目

继续完善“企业售后知识库与工单 Agent”。核心流程如下：

```text
Web / 移动端提问
  → API 鉴权与限流
  → LangGraph 售后工作流
  → 意图识别与信息补全
  → PostgreSQL/pgvector 混合检索与重排序
  → 生成带引用的处理建议
  → 必要时调用订单、保修或库存工具
  → 高风险操作进入人工审批
  → 后台 Worker 创建工单并触发 n8n 通知
  → 写入日志、Trace、Metrics、审计和评测样本
```

建议部署单元：

```text
Web / Mobile
      │
      ▼
API 服务 ───── Redis（缓存、限流、队列）
   │                    │
   │                    ▼
   │                 Worker ─── n8n / 外部工单系统
   ▼
PostgreSQL + pgvector
   │
   └── 业务数据、向量、Checkpoint、审计、版本与评测记录
```

## 月末验收标准

### 部署与恢复

- 一条命令可启动本地完整环境；核心服务均有健康检查。
- 预发布环境可部署固定版本镜像，能够回滚至上一个版本。
- 数据库迁移可重复执行；完成一次备份、清空测试库、恢复、校验的演练。
- 服务重启后，等待审批或执行中的工作流不会无故丢失。

### 质量与可靠性

- 关键纯函数与规则节点有单元测试，核心 API 有集成测试，主业务链路有端到端测试。
- 至少维护 100 条 RAG 测试问题和 30 条 Agent/工具调用场景。
- CI 自动执行格式检查、类型检查、测试、迁移检查和镜像构建。
- 创建工单、发送通知等副作用操作具备幂等键，重复请求不会产生重复工单。
- 模型、检索和外部工具均设置超时；重试有次数上限，只针对可重试错误。

### 安全与权限

- 日志、Trace 和错误响应不出现模型密钥、令牌、手机号、身份证号等敏感明文。
- 检索结果受用户/租户权限过滤，不能通过提问读取其他租户文档。
- 外部文档与工具返回内容被视为不可信数据，不能覆盖系统规则。
- 创建工单、发送消息、修改业务数据等工具采用最小权限；高风险操作必须人工确认。

### 指标与体验

- 仪表盘或报告至少包含请求量、错误率、P50/P95 延迟、Token/成本、检索无结果率、工具成功率和工作流完成率。
- 为项目设定并记录可解释的目标值，例如 API 非模型接口 P95、完整问答 P95、工具成功率和单次对话成本上限；不要照抄不符合本机条件的数字。
- Web 与移动端能展示流式状态、引用、工具执行、审批、失败重试和断线恢复。
- 最终版本附架构图、部署说明、环境变量模板、测试报告、恢复报告和已知限制。

## 第 1 天：定义生产目标与基线

**学习目标**：把“生产可用”转换为可检查的需求、指标和失败场景。

**核心知识**：功能需求与非功能需求；SLI、SLO 的基本概念；请求成功率、P95 延迟、成本、恢复时间；RAG/Agent 系统中的质量指标与系统指标不能互相替代。

**动手任务**：盘点当前综合项目的服务、数据源、工具和部署方式；画出现状架构图；列出模型超时、向量库不可用、Redis 重启、工具重复执行、恶意文档和移动端断线等 10 个故障场景；为本月项目设定可解释的目标值。

**当日产出/验收**：提交 `docs/production-readiness.md`，包含架构图、风险清单、指标定义、测量方式和月末验收表；每个指标都能回答“从哪里采集、如何判断通过”。

**建议时间**：1.5～2 小时。

## 第 2 天：环境配置与密钥管理

**学习目标**：使同一代码库安全运行在开发、测试和预发布环境。

**核心知识**：配置与代码分离；环境变量 Schema；启动时校验；密钥轮换；`.env.example` 与真实 `.env` 的区别；客户端绝不能持有模型或数据库密钥。

**动手任务**：用 Zod 定义配置 Schema，区分 API、Worker、数据库、Redis、模型、限流和观测配置；为开发、测试、预发布建立配置说明；搜索仓库中的硬编码密钥和敏感地址并清理。

**当日产出/验收**：缺少必需配置时服务启动失败并给出非敏感提示；仓库只提交 `.env.example`；Web/移动端构建产物中不存在服务端密钥；写出密钥轮换步骤。

**建议时间**：2 小时。

## 第 3 天：Docker Compose 生产基线

**学习目标**：把本地零散进程编排成可重复启动的服务集合。

**核心知识**：镜像与容器、网络、命名卷、健康检查、启动依赖、非 root 用户、多阶段构建；“容器启动”不等于“服务就绪”。

**动手任务**：为 API、Worker 和 Web 构建镜像；用 Compose 编排 PostgreSQL/pgvector、Redis、API、Worker 和前端；添加健康检查、持久卷和明确的端口；避免把密钥写入镜像层。

**当日产出/验收**：在干净环境中按 README 一条命令启动；健康检查能区分数据库未就绪与服务可用；停止再启动后数据库数据仍存在；记录镜像大小。

**建议时间**：2～2.5 小时。

## 第 4 天：PostgreSQL、pgvector 与迁移

**学习目标**：让业务表、向量数据和工作流状态具备可追踪的 Schema 变更。

**核心知识**：数据库迁移、唯一约束、索引、事务、连接池；向量索引参数需基于数据规模和测量调整；业务数据、文档元数据、向量和 Checkpoint 的边界。

**动手任务**：梳理用户、租户、文档、Chunk、会话、工作流、工单、审计和评测表；补充外键、唯一约束与必要索引；把手工建表改为迁移；为检索查询执行 `EXPLAIN` 并记录基线。

**当日产出/验收**：空数据库可从零迁移到最新版；重复执行迁移不会破坏数据；重复文档/工单被唯一约束阻止；核心检索有执行计划记录与索引说明。

**建议时间**：2～2.5 小时。

## 第 5 天：Redis 的清晰职责

**学习目标**：正确使用 Redis，而不是把它变成不可恢复的主数据库。

**核心知识**：缓存、TTL、限流计数、分布式锁和队列状态；Cache Aside；缓存穿透与击穿的基本处理；可丢数据和不可丢数据的区别。

**动手任务**：为会话热点数据或检索结果增加带版本的缓存键；实现 TTL 与显式失效；设计限流键和工单幂等键；确保关键业务结果最终写入 PostgreSQL。

**当日产出/验收**：首次查询未命中、第二次命中可观测；文档更新后旧缓存失效；Redis 被清空后系统只是变慢而不是丢失工单；不同租户的缓存键不会冲突。

**建议时间**：2 小时。

## 第 6 天：后台任务与 Worker

**学习目标**：把耗时或可延后操作移出请求链路，并保留任务进度与失败状态。

**核心知识**：队列、Producer、Consumer、任务状态、至少一次投递、幂等、有限重试、死信任务；适合后台执行的任务与必须同步返回的任务。

**动手任务**：选择文档入库、创建工单后的通知或评测任务接入 BullMQ/现有队列；定义任务载荷 Schema、幂等键、进度、重试和失败记录；API 返回可查询的任务 ID。

**当日产出/验收**：Worker 重启后任务可继续或安全重试；同一幂等键不会创建重复业务结果；客户端可查询 pending/running/succeeded/failed；失败任务有人工重放入口或命令。

**建议时间**：2～2.5 小时。

## 第 7 天：第一周一键环境整合

**学习目标**：验证新成员能依据文档独立启动项目并完成一次主流程。

**核心知识**：可重复环境、启动顺序、初始化脚本、Seed 数据、健康检查和故障可诊断性。

**动手任务**：从干净的数据库卷启动 Compose，执行迁移和最小 Seed；上传一份文档，完成一次检索问答和一次工单任务；分别停止 Redis、Worker、数据库，观察错误行为并修正最明显问题。

**当日产出/验收**：形成 `docs/local-runbook.md`；从下载依赖到跑通流程不依赖口头步骤；三种故障均有明确日志和用户可理解状态；提交第一周复盘。

**建议时间**：2.5 小时（周末整合）。

## 第 8 天：结构化日志与关联 ID

**学习目标**：从一次用户提问追踪到模型、检索、工具、Worker 和工单结果。

**核心知识**：结构化 JSON 日志、日志级别、`requestId`、`traceId`、`threadId`、`jobId`；业务字段与敏感字段；错误对象规范化。

**动手任务**：建立统一 Logger 和请求中间件；在 API、LangGraph 节点、RAG、工具与 Worker 中传递关联 ID；记录事件名、持续时间、状态和版本，不记录完整 Prompt、密钥或隐私明文。

**当日产出/验收**：用一个 `requestId` 可以检索出完整关键链路；错误日志含错误分类和安全堆栈；抽查日志不存在令牌、手机号和完整用户问题；日志格式有字段说明。

**建议时间**：2 小时。

## 第 9 天：端到端 Trace

**学习目标**：看清请求时间消耗在哪个模型、检索、节点或外部工具上。

**核心知识**：Trace、Span、父子关系、属性与事件；跨 API/Worker 传播上下文；采样；Trace 与日志互相跳转；模型输入内容的隐私风险。

**动手任务**：用 OpenTelemetry 或现有平台为 HTTP、数据库、RAG、LLM、LangGraph 节点和工具调用建立 Span；在进入队列时传播 Trace Context；关闭或脱敏敏感内容采集。

**当日产出/验收**：一次主流程能显示完整瀑布图；可定位最慢节点和失败工具；后台任务与原请求建立关联；故意制造超时后 Trace 中有明确错误标记。

**建议时间**：2～2.5 小时。

## 第 10 天：Metrics 与 P95 仪表盘

**学习目标**：用趋势和分位数衡量稳定性，而不是只看单次请求。

**核心知识**：Counter、Gauge、Histogram；P50/P95/P99；吞吐、错误率、队列积压、缓存命中率；高基数标签风险；业务指标和技术指标。

**动手任务**：采集请求量、错误率、端到端延迟、模型/检索/工具延迟、Token 与成本、缓存命中率、队列长度、工作流完成率、人工升级率和检索无结果率；制作最小仪表盘或报告脚本。

**当日产出/验收**：连续运行一组测试后可看到 P50/P95；指标不把用户 ID、问题文本作为标签；能从仪表盘定位一次人为制造的错误率上升；写出每个指标的解释。

**建议时间**：2 小时。

## 第 11 天：Prompt 与检索配置版本化

**学习目标**：让效果变化可追溯、可对比并可回滚。

**核心知识**：Prompt 模板 ID、语义版本、变量 Schema、模型配置、检索 Top-K/Rerank 配置；发布记录；线上记录实际使用版本而非“最新版本”。

**动手任务**：建立 Prompt Registry（可先用代码/数据库表实现）；为分类、查询改写、回答生成和风险判断模板建立版本；把模型、温度、检索参数与评测结果关联；增加版本回滚配置。

**当日产出/验收**：每条回答可查询 Prompt、模型、检索配置版本；旧版本仍可重放评测；变量缺失在调用前被校验；能在不改代码的情况下切回一个已验证版本。

**建议时间**：2～2.5 小时。

## 第 12 天：LangGraph 工作流版本与状态兼容

**学习目标**：升级节点和状态 Schema 时，不破坏仍在等待审批的旧流程。

**核心知识**：工作流版本、状态版本、Checkpoint 兼容、迁移函数、正在运行实例的处理策略；新旧图并存与禁止隐式升级。

**动手任务**：为图和状态添加 `workflowVersion`/`stateVersion`；模拟增加一个风险字段或节点；编写旧状态迁移函数；决定旧实例继续旧图、迁移或人工终止的规则。

**当日产出/验收**：旧 Checkpoint 能按明确策略恢复；不兼容状态不会静默运行；审计记录能显示执行版本；写出工作流升级与回滚说明。

**建议时间**：2 小时。

## 第 13 天：测试金字塔与契约测试

**学习目标**：用分层测试覆盖确定性逻辑、外部边界和真实业务链路。

**核心知识**：单元、集成、契约、端到端测试；Mock 与真实依赖的边界；数据库隔离；模型输出非确定性；测试数据工厂。

**动手任务**：为权限、路由、引用校验、幂等和重试规则补单元测试；为 API、PostgreSQL、Redis、队列补集成测试；为订单/工单工具定义请求响应契约；保留少量主链路 E2E。

**当日产出/验收**：测试按层级独立执行；关键规则不依赖真实模型即可测试；工具字段变化会导致契约测试失败；测试运行后不残留业务数据。

**建议时间**：2～2.5 小时。

## 第 14 天：RAG 与 Agent 回归门禁

**学习目标**：把“感觉回答变好了”改成可重复的发布判断。

**核心知识**：固定测试集、版本化期望、检索 Recall@K、引用正确性、无依据回答率、工具选择和参数正确率、工作流完成率；人工抽检与自动评分结合。

**动手任务**：整理至少 100 条 RAG 问题和 30 条 Agent 场景，覆盖正常、无证据、权限隔离、工具失败、需要审批和恶意输入；构建可重放脚本，对当前版本记录质量、延迟和成本基线。

**当日产出/验收**：生成 `reports/ai-regression-baseline.md`；每个失败案例能定位到检索、生成、工具或流程层；设定发布阻断阈值；第二周测试与观测能力全部串联。

**建议时间**：2.5 小时（周末整合）。

---

## 第 15 天：并发与流式性能基线

**学习目标**：在优化前用可重复负载测出当前吞吐和 P95 瓶颈。

**核心知识**：并发用户与每秒请求、首 Token 延迟、完整响应延迟、连接池、SSE 长连接、事件循环阻塞；压测环境与真实模型成本控制。

**动手任务**：用 k6 或 Artillery 编写三类脚本：普通 API、RAG 问答、SSE 流式对话；先用 Stub 模型测系统上限，再用少量真实请求测外部依赖；记录 CPU、内存、连接池和 P95。

**当日产出/验收**：提交性能基线报告，明确测试机器、并发、数据集和模型条件；找到至少一个实际瓶颈；不以单次最快结果代替分位数。

**建议时间**：2～2.5 小时。

## 第 16 天：限流、配额与背压

**学习目标**：防止单个用户或突发流量耗尽模型额度、连接与 Worker。

**核心知识**：固定窗口/滑动窗口/令牌桶的应用差异；用户、租户和接口维度配额；并发上限；队列背压；`429` 与重试提示。

**动手任务**：基于 Redis 实现用户与租户限流；为高成本模型接口配置更严格额度；设置同时运行工作流数与队列长度上限；客户端展示等待、降级或稍后重试状态。

**当日产出/验收**：突发请求被稳定限制而不是拖垮服务；不同租户互不占用配额；响应包含可理解的重试信息；队列积压达到阈值时停止无界接单。

**建议时间**：2 小时。

## 第 17 天：分层缓存与正确失效

**学习目标**：在不牺牲权限、时效和回答正确性的前提下降低延迟与成本。

**核心知识**：文档解析缓存、Embedding 缓存、检索缓存、模型响应缓存；缓存键必须包含租户、权限、数据版本、Prompt/模型/检索版本；不适合缓存的个性化和高风险结果。

**动手任务**：选择收益最大的两层缓存落地；加入命中率和节省时间/成本指标；实现文档更新、权限变化和 Prompt 发布后的失效；禁止缓存创建工单等副作用。

**当日产出/验收**：重复安全查询的延迟或成本可测量下降；跨租户相同问题不会共享受限结果；版本变化后不会返回旧答案；报告命中率和失效策略。

**建议时间**：2～2.5 小时。

## 第 18 天：超时、重试与调用预算

**学习目标**：让一次失败快速结束或有限恢复，避免层层重试放大延迟和成本。

**核心知识**：连接与请求超时、总调用预算、指数退避与抖动、可重试错误、取消传播、重试风暴；LLM、数据库与副作用工具的不同策略。

**动手任务**：为模型、Embedding、RAG、数据库、工单和通知设置独立超时；统一可重试错误分类；用总预算限制 Agent 循环与工具次数；客户端停止生成时向下游传播取消信号。

**当日产出/验收**：模拟 429、5xx、超时和用户取消；重试次数可从 Trace 看见且有上限；400/401 和校验错误不重试；创建工单不会因网络重试重复执行。

**建议时间**：2～2.5 小时。

## 第 19 天：熔断、降级与故障隔离

**学习目标**：单个外部依赖故障时保住系统的可用部分。

**核心知识**：熔断器 Closed/Open/Half-Open；Fallback；Bulkhead；主模型与备用模型；只读回答、人工转接和稍后处理等业务降级。

**动手任务**：为模型或工单系统实现最小熔断；设计模型不可用、RAG 不可用、Redis 不可用、通知不可用的降级矩阵；把非关键通知失败与核心工单状态隔离。

**当日产出/验收**：连续故障达到阈值后停止无效调用；半开状态能探测恢复；Redis 故障不会破坏 PostgreSQL 中的核心数据；用户收到准确的降级提示而非虚假成功。

**建议时间**：2 小时。

## 第 20 天：数据脱敏、保留与租户隔离

**学习目标**：控制敏感数据在输入、日志、Trace、模型和存储中的流向。

**核心知识**：数据分类、最小收集、传输与静态加密概念、脱敏、保留期限、删除流程；租户 ID 与权限过滤；备份同样包含敏感数据。

**动手任务**：列出项目中的姓名、手机号、地址、订单号、对话和上传文档；在日志/Trace 前做脱敏；检索 SQL 强制带租户和权限条件；实现删除用户对话或文档后的向量与缓存联动删除。

**当日产出/验收**：跨租户访问测试全部失败；日志只显示必要的掩码数据；删除一份文档后原文、Chunk、向量和缓存均不可检索；提交数据流与保留策略说明。

**建议时间**：2～2.5 小时。

## 第 21 天：Prompt Injection 与不可信内容演练

**学习目标**：防止用户、网页、PDF 或工具返回值中的指令越权控制 Agent。

**核心知识**：直接/间接 Prompt Injection；指令与数据分离；外部内容不可信；输出校验；权限边界必须由代码实施；提示词不能替代安全控制。

**动手任务**：准备至少 15 条攻击样例，包括“忽略系统提示”、文档内隐藏指令、诱导泄露系统 Prompt、跨租户查询、让工具删除/发送数据；增加上下文标记、工具白名单、参数 Schema、权限校验和敏感输出拦截。

**当日产出/验收**：攻击集有期望行为和实际结果；模型即使建议越权调用，执行层也会拒绝；外部文档内容不会变更工具权限；提交第三周安全与可靠性复盘。

**建议时间**：2.5 小时（周末整合）。

---

## 第 22 天：工具最小权限与人工审批

**学习目标**：把 Agent 的“会调用工具”升级成可授权、可审批、可审计的业务能力。

**核心知识**：读写工具分离、最小权限、用户授权上下文、参数白名单、幂等、审批快照、审批后参数不可悄悄变化、审计不可依赖模型自述。

**动手任务**：给订单查询、保修查询、创建工单和发送通知定义独立权限；高风险工具先生成不可变的执行预览，用户/客服确认后执行；记录操作者、时间、参数摘要、结果与工作流版本。

**当日产出/验收**：普通用户不能调用客服专用工具；审批前不能产生副作用；篡改审批后的参数会被拒绝；重复确认只生成一个工单；审计页面可还原操作链路。

**建议时间**：2～2.5 小时。

## 第 23 天：备份与恢复演练

**学习目标**：证明数据库、向量、配置和文档不是“理论上可以恢复”。

**核心知识**：全量备份、恢复点、RPO/RTO、数据库与对象文件的一致性、备份加密与访问；向量可重建但重建有时间和成本。

**动手任务**：备份测试环境的 PostgreSQL/pgvector、文档存储、Prompt/工作流版本配置；记录备份时间和校验；在隔离的空测试库中恢复，并抽查用户、文档、向量、Checkpoint、工单和审计记录。

**当日产出/验收**：提交 `docs/backup-restore-drill.md`，包含命令、耗时、恢复验证和失败点；至少完成一次真实恢复；恢复环境不会误连生产/正式外部工具；明确哪些数据可重建。

**建议时间**：2～2.5 小时。

## 第 24 天：建立 CI 质量门禁

**学习目标**：让每次提交自动证明代码、迁移和 AI 能力没有明显退化。

**核心知识**：CI Job、依赖缓存、服务容器、密钥隔离、制品；快速检查与慢速 AI 回归分层；分支保护和失败阻断。

**动手任务**：配置 GitHub Actions，依次执行格式检查、Lint、类型检查、单元测试、集成测试、迁移检查、依赖/密钥扫描和镜像构建；把小型离线 AI 回归加入 PR，把完整回归设计为手动或定时任务。

**当日产出/验收**：故意引入类型错误、失败迁移和回归退化时 CI 会阻止通过；日志不泄露密钥；构建产物带提交 SHA/版本号；README 显示当前流水线状态。

**建议时间**：2～2.5 小时。

## 第 25 天：预发布部署与回滚

**学习目标**：把固定版本安全发布到预发布环境，并能在失败时回到已知版本。

**核心知识**：不可变镜像、版本标签、启动/就绪检查、迁移顺序、滚动发布概念、向后兼容、回滚与数据库迁移的关系。

**动手任务**：把镜像部署到可用的预发布环境或本地模拟环境；发布前执行迁移与 Smoke Test；记录镜像、Prompt 和工作流版本；人为发布一个健康检查失败版本并执行回滚。

**当日产出/验收**：`docs/deploy-runbook.md` 覆盖部署、验证、回滚和负责人；固定版本可重复部署；回滚后核心问答和工单流程恢复；未通过就绪检查的实例不接收请求。

**建议时间**：2～2.5 小时。

## 第 26 天：Web 端生产体验

**学习目标**：让 Web 用户在慢请求、失败和审批场景下始终知道系统状态与下一步。

**核心知识**：流式状态机、断线重连、请求去重、取消、重试、引用预览、工具进度、审批确认、可访问性；技术错误与用户提示分离。

**动手任务**：完善提问、检索、生成、工具等待、审批、完成和失败状态；支持 SSE 断线后按事件 ID 或任务 ID恢复；为引用提供原文定位；危险操作展示参数和影响范围。

**当日产出/验收**：刷新页面不丢长任务状态；重复点击不会重复建单；网络中断后可恢复或明确重试；键盘可完成主要流程；错误页面不显示堆栈和内部信息。

**建议时间**：2～2.5 小时。

## 第 27 天：移动端弱网与系统能力

**学习目标**：利用移动端经验把 Agent 变成真实可用的现场工具。

**核心知识**：应用前后台切换、弱网、离线草稿、任务轮询/推送、文件和相机权限、深链接、敏感信息本地存储；移动端不能假设长连接永久存在。

**动手任务**：实现问题草稿与安全的任务 ID 持久化；切到后台再回来后恢复任务；为拍照/上传说明书增加权限与失败处理；从通知深链接进入待审批工单；避免本地保存模型密钥和不必要隐私数据。

**当日产出/验收**：飞行模式切换、前后台切换、进程重启三种场景均有明确行为；重复恢复不会重复提交；权限拒绝有替代路径；完成一段移动端流程录屏。

**建议时间**：2～2.5 小时。

## 第 28 天：端到端与故障注入演练

**学习目标**：在接近真实的环境中验证系统的恢复、降级和审计能力。

**核心知识**：Smoke Test、E2E、故障注入、演练记录、恢复判定；不能只验证成功路径。

**动手任务**：在预发布执行至少 12 个场景：普通问答、无证据、跨租户、恶意文档、审批拒绝、重复建单、模型超时、工单 5xx、Redis 重启、Worker 重启、移动端断线和数据库短暂不可用；检查日志、Trace、Metrics 与审计。

**当日产出/验收**：形成 `reports/staging-drill.md`，每个场景包含预期、实际、证据和缺陷；P0/P1 缺陷当日修复或阻止发布；第四周部署链路可完整重跑。

**建议时间**：2.5 小时（周末整合）。

## 第 29 天：成本与 P95 定向优化

**学习目标**：基于指标选择一到两个高收益优化，而不是盲目改代码。

**核心知识**：成本拆分（输入/输出 Token、Embedding、Rerank、存储与外部工具）；延迟拆分；上下文裁剪、小模型路由、并行、缓存、批处理的收益与风险；优化后必须重跑质量回归。

**动手任务**：从 Trace 和 Metrics 找出最大成本项与 P95 瓶颈；选择两项优化，例如减少无效上下文、分类使用更轻模型、独立检索并行、Embedding 批处理或连接池调整；用相同数据集比较前后质量、成本与 P95。

**当日产出/验收**：提交前后对比表，写清环境和样本量；至少一项指标有可重复改善，且 RAG/Agent 回归未低于门禁；效果下降的优化要撤回并记录原因。

**建议时间**：2～2.5 小时。

## 第 30 天：发布候选版、复盘与第 12 月交接

**学习目标**：冻结一个可演示、可部署、可解释的版本，并把成果转化为作品集素材。

**核心知识**：Release Candidate、变更日志、已知限制、运行手册、事故响应、交接文档；技术成果要用业务问题、方案、指标和权衡表达。

**动手任务**：打 `v1.0.0-rc` 标签或等价版本；从零部署并跑 Smoke Test；整理架构图、数据流图、部署与回滚、备份恢复、API、权限、安全、测试、评测、性能和成本报告；录制 Web 与移动端完整演示；复盘本月关键决策。

**当日产出/验收**：月末验收清单逐项有证据；另一名开发者仅按 README 能启动并理解项目；演示覆盖“知识问答带引用 → 工具查询 → 人工审批 → 创建工单 → 查看 Trace/指标”；列出未完成项与风险，不伪装成已解决。

**建议时间**：2.5 小时。
