# 第 8 月：用 LangGraph.js 构建可控的 AI 工作流

## 本月定位

本月从“能回答问题的高级 RAG 知识库”升级到“能按业务规则完成任务的 AI 工作流”。主线语言仍然是 TypeScript，使用 LangGraph.js 组织状态、节点、条件分支、循环、并行和人工审批；Python 只作为可选的文档处理辅助，不安排算法题、模型训练或复杂数学。

学习原则是**先 Workflow，后 Agent**：凡是步骤已知、风险可判断、操作可审计的业务，优先写成确定性或半确定性状态图。模型只负责分类、信息提取、生成建议等模糊任务，创建工单、发送通知等副作用操作必须由代码、权限和人工确认约束。

## 前置能力

- 能使用 TypeScript、Node.js 和 `async/await` 开发服务端程序。
- 能用 Fastify 或 NestJS 编写 REST API，并理解 SSE 或流式响应。
- 会使用 PostgreSQL，了解 Redis、Docker Compose 和环境变量管理。
- 已完成一个 RAG 知识库，支持检索、引用、元数据过滤和基础评测。
- 理解 LLM 结构化输出、Tool Calling、超时、重试和错误处理。
- 前端或移动端能够消费 API，并维护页面级状态。

如果某项前置能力暂时不牢，本月只补“项目实际需要的部分”，不要停下来重新学完整课程。

## 本月目标

完成本月后，你应该能够：

1. 根据业务需求判断哪些步骤使用普通代码、RAG、LLM 节点或人工审批。
2. 使用 LangGraph.js 定义状态 Schema、节点、边、条件边、循环、并行和子图。
3. 使用 Checkpoint 保存执行状态，实现中断、恢复和会话隔离。
4. 为外部调用设计超时、有限重试、幂等、补偿和失败降级。
5. 用 Interrupt 实现人工审批，阻止高风险操作自动执行。
6. 把工作流事件以 SSE 推送给前端，展示进度、证据、审批和错误状态。
7. 为每个节点编写单元测试，为主链路编写集成测试，并记录 Trace。
8. 交付一套可演示、可恢复、可审计的售后问题处理工作流。

## 推荐技术栈

- Node.js 20+、TypeScript
- LangGraph.js、主流模型官方 TypeScript SDK
- Zod：状态与模型输出校验
- Fastify 或 NestJS：工作流 API 与 SSE
- PostgreSQL：业务数据、工单、审计记录
- LangGraph Checkpoint 持久化组件；本地学习可先用内存实现
- Redis：可选，用于缓存、事件广播或任务状态
- Vitest：单元测试与集成测试
- OpenTelemetry 或可用的 LLM Trace 平台：链路追踪
- React、Vue、Flutter 或现有移动端技术：进度与审批界面
- Docker Compose：本地集成环境

## 月度项目

构建“售后问题处理工作流”，主链路如下：

```text
用户问题
  → 问题分类
  → 判断信息是否完整
  → 必要时向用户澄清（可暂停）
  → RAG 检索产品知识
  → 生成带引用的解决方案
  → 风险判断
  → 高风险操作人工审批（可暂停）
  → 创建工单（幂等）
  → 通知用户（失败可补偿/重试）
  → 写入审计与评测数据
```

建议状态至少包含：`requestId`、`threadId`、用户问题、产品信息、分类结果、缺失字段、澄清记录、检索证据、解决方案、风险等级、审批状态、工单 ID、通知状态、错误信息、节点执行记录和版本号。不要把所有数据塞进一段消息历史。

## 本月节奏

- 第 1 周：需求拆解、状态 Schema、节点与分支。
- 第 2 周：循环、并行、子图、Checkpoint 与恢复。
- 第 3 周：可靠性、幂等、补偿、人工审批和流式事件。
- 第 4 周：测试、Trace、前端可视化、综合联调与发布。
- 每日建议 1.5～2.5 小时；周末用于整合，不额外堆叠新框架。

## 第 1 天：从业务需求画出可控流程

**学习目标**：理解 Workflow 与 Agent 的边界，把自然语言需求拆成明确步骤。

**核心知识**：确定性节点、LLM 节点、RAG 节点、人工节点、副作用节点；输入、输出、失败路径；为什么支付、建单、通知不能交给模型自由决定。

**动手任务**：阅读月度项目描述，画出主流程和三条异常流程：信息不足、检索无证据、创建工单失败。给每个节点标注“代码 / LLM / RAG / 人工”。

**当日产出/验收**：提交 `docs/workflow-requirements.md` 和一张 Mermaid 流程图；每个节点都有输入、输出、失败策略和执行主体。

**建议时间**：1.5 小时。

## 第 2 天：建立 LangGraph.js 最小工程

**学习目标**：跑通第一个无模型依赖的 LangGraph.js 状态图。

**核心知识**：Graph、State、Node、Edge、Start、End；图的编译与调用；为什么先用纯函数节点验证流程。

**动手任务**：初始化 TypeScript 项目，配置 ESLint、Vitest 和环境变量；创建“接收问题 → 标准化文本 → 返回结果”的三节点工作流。

**当日产出/验收**：`npm run dev` 可执行示例；`npm test` 至少通过一个测试；缺失环境变量时有明确错误而不是静默失败。

**建议时间**：2 小时。

## 第 3 天：设计业务状态 Schema

**学习目标**：用显式状态代替散乱变量和无限增长的消息历史。

**核心知识**：状态字段、默认值、Reducer、可选字段、只读上下文；运行状态与业务持久化数据的区别；Zod 运行时校验。

**动手任务**：定义 `AfterSalesState`，覆盖请求标识、用户输入、产品信息、分类、证据、方案、风险、审批、工单和通知；为数组字段设计合并策略。

**当日产出/验收**：状态 Schema 能拒绝非法风险等级和缺失的请求 ID；写出状态字段说明表；至少 5 个 Schema 测试通过。

**建议时间**：2 小时。

## 第 4 天：编写可测试的节点

**学习目标**：让节点职责单一、依赖可注入、输入输出可预测。

**核心知识**：节点纯函数化、依赖注入、结构化输出、状态局部更新；避免节点直接修改共享对象；模型响应与业务状态隔离。

**动手任务**：实现问题清洗、产品信息提取和问题分类节点；先用 Stub 模型，再接真实 LLM；对 LLM 输出使用 Zod 校验。

**当日产出/验收**：三个节点均有单元测试；模型返回非法 JSON 时进入显式错误分支；日志不包含密钥和完整隐私数据。

**建议时间**：2～2.5 小时。

## 第 5 天：条件分支与路由函数

**学习目标**：根据业务状态选择下一条明确路径。

**核心知识**：Conditional Edge、路由函数、枚举结果、默认分支；业务规则优先于模型自由路由；未知分类的安全降级。

**动手任务**：在分类后增加路由：常见咨询进入 RAG，信息不足进入澄清，高风险投诉直接进入人工处理，未知类别进入兜底。

**当日产出/验收**：为四条分支各写一个测试；路由函数不调用外部 API；任何输入都有可预测出口。

**建议时间**：2 小时。

## 第 6 天：澄清信息与有限循环

**学习目标**：设计能回到前序步骤、但不会无限运行的澄清循环。

**核心知识**：循环边、循环计数、退出条件、最大步数；状态累积；何时暂停等待用户，何时直接失败或转人工。

**动手任务**：实现“检查缺失字段 → 生成澄清问题 → 接收补充信息 → 再检查”的循环；最多澄清 3 次，超限后转人工。

**当日产出/验收**：完整信息一次通过；缺失信息能生成具体问题；第三次仍不完整时必定退出循环；测试覆盖三种情况。

**建议时间**：2～2.5 小时。

## 第 7 天：第一周整合与流程评审

**学习目标**：形成可以从输入运行到分类/澄清出口的第一版流程。

**核心知识**：状态图可读性、节点命名、边界条件、错误路径；用业务案例而非技术 Demo 验证流程。

**动手任务**：整合前六天代码，准备 10 个售后案例，逐条运行并记录经过的节点；修正状态字段和路由规则。

**当日产出/验收**：10 个案例均能落到合理出口；输出一份第一周复盘，列出至少 3 个设计调整及原因；所有测试持续通过。

**建议时间**：2.5 小时（周末整合）。

## 第 8 天：接入已有 RAG 知识库

**学习目标**：把上月知识库作为受控节点接入工作流，而不是在图内重写 RAG。

**核心知识**：检索服务接口、查询改写、元数据过滤、Top-K、证据结构；超时和无结果的状态表示。

**动手任务**：实现 `retrieveKnowledge` 节点，根据产品型号、地区和版本过滤；统一返回文档 ID、片段、分数和来源 URL。

**当日产出/验收**：已知问题能返回可引用证据；无证据时不生成虚构答案，而是走“补充信息/人工”分支；记录检索耗时。

**建议时间**：2 小时。

## 第 9 天：生成带引用的解决方案

**学习目标**：约束 LLM 只基于证据生成结构化方案。

**核心知识**：上下文组装、引用 ID、结构化输出、证据不足声明；将“生成结果”与“是否允许执行”分离。

**动手任务**：实现方案生成节点，输出摘要、操作步骤、引用列表、置信提示和建议动作；加入引用存在性校验。

**当日产出/验收**：每条事实性建议都能定位到证据；虚假引用被校验器拦截；无证据案例明确返回升级人工建议。

**建议时间**：2～2.5 小时。

## 第 10 天：并行执行独立任务

**学习目标**：识别真正可以并行的节点，并正确合并结果。

**核心知识**：Fan-out/Fan-in、并行状态更新、Reducer、竞态条件；并行带来的延迟收益与错误复杂度。

**动手任务**：在信息完整后并行执行“知识检索”和“用户历史摘要/保修状态查询”，随后合并进入方案生成。

**当日产出/验收**：并行结果不会互相覆盖；单个非关键分支失败时能降级；比较串行与并行的总耗时并记录结果。

**建议时间**：2 小时。

## 第 11 天：用子图管理复杂模块

**学习目标**：将澄清、RAG 处理等模块封装为可复用子图。

**核心知识**：Subgraph、父子状态映射、输入输出边界、命名空间；何时拆子图，何时保留普通函数。

**动手任务**：将“澄清循环”和“RAG 检索—生成—引用校验”分别封装为子图，主图只关心模块级结果。

**当日产出/验收**：两个子图能独立测试；父图状态不会泄露无关的子图内部字段；主图代码明显简化且流程图保持一致。

**建议时间**：2～2.5 小时。

## 第 12 天：Checkpoint 与线程隔离

**学习目标**：让每次工作流执行可持久化，并区分不同用户会话。

**核心知识**：Checkpointer、`thread_id`、Checkpoint 生命周期、运行配置；会话 ID、请求 ID 与业务工单 ID 的区别。

**动手任务**：先接入内存 Checkpointer，再接项目可用的持久化实现；为每次运行生成明确的 `threadId` 和 `requestId`。

**当日产出/验收**：服务重启后可恢复测试流程（若本地持久化实现支持）；两个 thread 的状态互不串联；可查询最近一次 Checkpoint。

**建议时间**：2 小时。

## 第 13 天：暂停与恢复执行

**学习目标**：支持工作流等待用户补充信息后，从原位置继续。

**核心知识**：Interrupt、Resume Command、恢复输入、重复执行风险；Checkpoint 与中断的配合。

**动手任务**：澄清节点发出 Interrupt，API 返回“等待用户输入”；用户提交产品型号后，使用同一 `threadId` 恢复运行。

**当日产出/验收**：刷新页面或稍后提交信息都能继续；恢复时不会从头重复分类；无效 thread 返回明确的 404/业务错误。

**建议时间**：2～2.5 小时。

## 第 14 天：第二周故障恢复演练

**学习目标**：验证流程在重启、超时和用户延迟回复情况下仍可恢复。

**核心知识**：恢复点、状态版本、过期会话、重复提交；恢复能力不是“重新运行全部流程”。

**动手任务**：设计并执行四个演练：服务重启、RAG 暂时不可用、用户隔天回复、同一恢复请求提交两次。

**当日产出/验收**：提交 `docs/recovery-drill.md`，记录每个故障的预期、实际和修正；关键节点无重复副作用；第二周全部测试通过。

**建议时间**：2.5 小时（周末整合）。

## 第 15 天：统一超时与错误分类

**学习目标**：让网络失败、业务拒绝和数据非法得到不同处理。

**核心知识**：调用超时、可重试错误、不可重试错误、业务错误、取消信号；错误码与用户提示分离。

**动手任务**：为 LLM、RAG、工单和通知调用封装统一超时；定义错误类型与状态字段；在图中加入错误路由节点。

**当日产出/验收**：模拟超时、401、429、5xx 和非法数据；每类错误走到正确路径；前端不会看到堆栈或内部密钥信息。

**建议时间**：2 小时。

## 第 16 天：有限重试与退避

**学习目标**：仅对值得重试的瞬时故障执行有限重试。

**核心知识**：Retry Policy、指数退避、抖动、最大次数、Retry-After；为什么验证失败和权限失败不能盲目重试。

**动手任务**：为检索和通知设置不同重试策略；记录每次尝试；超过上限后进入降级或人工处理。

**当日产出/验收**：429/5xx 能有限重试并最终成功或明确失败；400/401 直接停止；测试中不存在无限循环和长时间挂起。

**建议时间**：2 小时。

## 第 17 天：幂等地创建工单

**学习目标**：防止恢复、重试或重复点击导致重复工单。

**核心知识**：幂等键、唯一约束、去重表、请求状态；“至少一次执行”环境中的副作用控制。

**动手任务**：使用 `requestId + actionType` 生成幂等键；在数据库建立唯一约束；创建工单前查询执行记录，成功后保存外部工单 ID。

**当日产出/验收**：同一请求并发提交或恢复两次只产生一个工单；返回相同工单 ID；有自动化测试证明而不是人工观察。

**建议时间**：2～2.5 小时。

## 第 18 天：补偿与部分失败处理

**学习目标**：处理“工单已创建但通知失败”等无法用事务整体回滚的情况。

**核心知识**：补偿动作、Saga 思想、最终一致性、可重放任务；哪些操作能撤销，哪些只能追加纠正记录。

**动手任务**：设计副作用表；通知失败时保留工单并进入待补发队列，而不是删除工单；如创建了临时资源，则提供安全取消动作。

**当日产出/验收**：写出补偿矩阵；模拟通知连续失败，工单状态仍一致且可稍后补发；补偿动作自身也具备幂等性。

**建议时间**：2 小时。

## 第 19 天：风险判断与人工审批

**学习目标**：在高风险动作前强制暂停并等待授权。

**核心知识**：规则判断与模型判断组合、审批上下文、批准/拒绝/修改、权限校验、审批过期；Human-in-the-loop。

**动手任务**：根据投诉等级、费用、账户操作和模型不确定性计算风险；中高风险进入审批 Interrupt；审批者可批准、拒绝或修改方案。

**当日产出/验收**：未审批绝不执行建单/通知；普通用户不能审批自己的高风险请求；审批操作写入审计日志；拒绝路径可正常结束。

**建议时间**：2～2.5 小时。

## 第 20 天：流式事件与进度协议

**学习目标**：把图的执行过程转换成前端可消费的稳定事件。

**核心知识**：节点事件、Token 事件、自定义进度事件、SSE；事件序号、重连、最终状态；内部 Trace 与用户进度的区别。

**动手任务**：定义 `workflow_started`、`node_started`、`evidence_ready`、`approval_required`、`node_failed`、`workflow_completed` 等事件，通过 SSE 输出。

**当日产出/验收**：事件包含 thread、节点、时间、序号和安全载荷；断线重连可获取当前状态；不会把完整 Prompt 或隐私数据推给客户端。

**建议时间**：2 小时。

## 第 21 天：第三周可靠性评审

**学习目标**：确认每个外部副作用都有超时、重试、幂等和审计策略。

**核心知识**：故障模式清单、风险优先级、数据一致性、人工兜底；从“能跑”转向“失败也可控”。

**动手任务**：对每个节点填写可靠性表：是否外部调用、超时、重试次数、幂等键、补偿动作、人工兜底、告警条件。

**当日产出/验收**：没有策略空白的副作用节点；完成至少 5 个故障注入测试；输出第三周复盘与剩余风险列表。

**建议时间**：2.5 小时（周末整合）。

## 第 22 天：前端工作流进度可视化

**学习目标**：利用前端/移动端优势，把后台状态图变成清晰的用户体验。

**核心知识**：服务端状态与 UI 状态映射、步骤条、进行中/等待/失败/完成状态；刷新恢复和弱网处理。

**动手任务**：实现工作流详情页，显示已完成节点、当前节点、下一步、耗时和错误；通过 SSE 实时更新，通过状态 API 支持刷新恢复。

**当日产出/验收**：用户能区分“正在处理”“等待补充信息”“等待审批”“失败可重试”；断网重连后进度不倒退、不重复。

**建议时间**：2～2.5 小时。

## 第 23 天：证据、澄清与审批界面

**学习目标**：为工作流中的关键人机交互提供结构化界面。

**核心知识**：引用卡片、原文定位、动态表单、审批差异展示、确认语义；避免用一个聊天气泡承载全部操作。

**动手任务**：实现证据侧栏、澄清表单和审批面板；审批面板显示方案、证据、风险原因和将执行的实际动作。

**当日产出/验收**：审批者无需查看日志即可理解影响；修改后的方案与原方案有差异标识；重复点击被前后端共同阻止。

**建议时间**：2～2.5 小时。

## 第 24 天：节点单元测试

**学习目标**：在不运行整张图、不调用真实外部服务的情况下验证节点行为。

**核心知识**：Mock/Stub、固定模型响应、依赖注入、表格驱动测试；测试状态增量而非实现细节。

**动手任务**：为分类、缺失字段检查、检索结果转换、引用校验、风险判断和路由函数补齐测试。

**当日产出/验收**：核心纯逻辑节点分支覆盖充分；测试不依赖网络和真实模型；失败信息能快速指出业务规则问题。

**建议时间**：2 小时。

## 第 25 天：图级集成测试

**学习目标**：验证跨节点状态流转、中断恢复和副作用约束。

**核心知识**：测试 Checkpointer、场景夹具、状态快照、端到端与集成测试边界；确定性回放。

**动手任务**：编写至少 8 条流程测试：直接解决、需要澄清、无证据、高风险审批通过/拒绝、建单超时、通知失败、重复恢复。

**当日产出/验收**：8 条流程均验证最终状态和节点路径；外部服务全部可替换为测试双；失败场景不会产生重复工单。

**建议时间**：2～2.5 小时。

## 第 26 天：Trace、日志与审计

**学习目标**：能够回答“这次工作流为什么得到这个结果”。

**核心知识**：Trace、Span、Correlation ID、结构化日志、指标、审计日志；Prompt/模型版本；隐私脱敏。

**动手任务**：给每个节点记录开始、结束、耗时、结果类型和错误；关联 `requestId`、`threadId`；记录模型与 Prompt 版本以及审批人。

**当日产出/验收**：从任一失败请求可定位失败节点和输入类别；日志中无密钥、Token、完整手机号等敏感信息；审计记录不可被普通用户修改。

**建议时间**：2 小时。

## 第 27 天：接口契约与安全检查

**学习目标**：让工作流通过稳定 API 被 Web 和移动端安全调用。

**核心知识**：启动、查询、恢复、审批、取消接口；鉴权、资源归属、输入校验、Prompt Injection 边界、限流。

**动手任务**：整理 OpenAPI 契约；检查每个接口的认证和授权；将检索文本视为不可信内容；对工具参数再次做服务端校验。

**当日产出/验收**：越权读取和审批均返回拒绝；恶意文档内容不能绕过工具权限；API 示例可直接被前端调用。

**建议时间**：2 小时。

## 第 28 天：全链路整合与真实案例验收

**核心知识**：端到端联调、测试数据、验收场景、可重复环境；业务指标与技术指标。

**动手任务**：用 Docker Compose 启动依赖，运行至少 20 个真实售后案例；记录成功率、平均/P95 延迟、RAG 无证据率和人工介入率。

**当日产出/验收**：20 个案例都有结果和 Trace；主流程无阻断错误；核心失败能恢复或转人工；输出一份验收记录。

**建议时间**：2.5 小时（周末整合）。

## 第 29 天：代码重构、文档与演示准备

## 与第 9 月 Agent / MCP 的衔接

下月不要推翻本月状态图，而是在可控框架内做局部升级：

- 将“复杂问题诊断”升级为受限 Agent，让它在知识检索、账户查询、设备诊断等只读工具中动态选择。
- 用 MCP 标准化接入知识库、订单查询和工单系统，但服务端仍执行身份校验、参数校验和权限控制。
- 为 Agent 增加最大步数、允许工具列表、成本预算、超时和 Trace。
- 保留 LangGraph 作为外层编排器，继续负责审批、Checkpoint、重试、幂等、补偿和最终状态。
- 创建工单、发通知、修改账户等写操作仍通过确定性节点，并在高风险场景保留人工审批。

完成本月后，你的核心成果不是“会调用 LangGraph API”，而是能把一个包含 LLM 不确定性和真实业务副作用的需求，设计成可暂停、可恢复、可测试、可观测、对用户友好的生产型工作流。
